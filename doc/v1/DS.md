## 先看懂这几个词

后面会反复用到，先解释一遍。已经懂的话可以跳过。

| 词 | 大白话解释 |
|---|---|
| **localStorage** | 浏览器自带的一个小仓库。网页把数据存在这里，关掉浏览器再打开还在。同一台设备、同一个浏览器，就有这一份。 |
| **Capacitor Preferences** | Capacitor 官方提供的存储插件。安卓上它落在系统的 SharedPreferences 里，比 localStorage 稳当——只有卸载 App 才会清掉。 |
| **JSON** | 一种把数据写成文本的格式。长这样：`{ "text": "写报告", "completed": false }`。因为是人能看懂的文本，所以很适合用来做备份文件。 |
| **四象限** | 把任务按「重要 / 紧急」两个维度分成四类：I 重要且紧急、II 重要不紧急、III 紧急不重要、IV 都不占。 |
| **Markdown（.md）** | 一种用纯文本排版的格式。`# 标题`、`- 列表` 这样写，看起来还是普通文字，但能转成好看的样式。 |
| **PDF** | 排版固定、到哪台设备上看起来都一样的文档格式。 |
| **WebDAV** | 一种「网盘的标准接口」。用它可以像操作文件夹一样操作网盘上的文件，不用自己写服务器程序。 |
| **跨域（CORS）** | 浏览器的安全规矩：网页 A 想访问网站 B 的接口，如果网站 B 没明确说「允许」，浏览器就会拦下来。**这条规矩只拦网页，不拦手机 App**，后面会重点提到。 |
| **备份** | 把数据多留几份。万一手滑删了、或者程序出错把数据写坏了，还能从旧的副本找回来。 |

## 一、技术栈与模块划分

### 1.1 用什么技术

| 部分 | 选择 | 为什么 |
|---|---|---|
| 页面 | 一个 `index.html` | 没有构建步骤，本地双击就能看效果（正式发布见 1.9） |
| 样式 | 一个 `css/style.css` | 全部外观集中在一处，好改 |
| 代码 | 原生 JavaScript（不用框架） | 不装任何第三方库，也就不会因为库升级而坏掉 |
| 本地存储 | 浏览器自带的 localStorage | 不用买服务器，数据就在用户自己设备上 |
| 安卓端的额外保险 | Capacitor Preferences（官方插件） | 安卓系统会回收 localStorage，见 2.1 |
| 云端同步 | 坚果云 WebDAV | 详见 2.5 |
| 打包成 App | Capacitor | 把网页包成安卓 App |
| 测试 | Node 脚本 | 不装任何东西就能跑 |

**一条总原则：不引入任何第三方代码库。** 不用 React / Vue，不用 jQuery，不用 npm 装包。全部代码是我们自己写的，出问题好查，也不会因为别人更新了库而突然跑不动。

### 1.2 项目目录长什么样

```
TimeScheduler_v2/
├── index.html          唯一的页面
├── css/
│   └── style.css       唯一的样式文件
├── js/                 全部代码，共 13 个文件
├── test/               自动化测试脚本
└── doc/
    └── v1/
        ├── FS.md       需求：做什么
        └── DS.md       设计：怎么做（本文）
```

只有一个页面、一个样式文件、一个 js 文件夹。没有 `node_modules`，没有打包产物。

### 1.3 每个文件负责什么

代码按「谁不依赖谁」分成几层。这样分的好处是：改上面一层不会影响下面一层。

```
入口层    app.js                          程序从这里启动
   ↑
交互层    drag.js（拖拽） date-nav.js（切日期） theme.js（主题）
业务层    task-ops.js（增删改勾选）
   ↑
渲染层    render.js                        把数据画成页面
   ↑
数据层    store.js                         读写数据，只此一家
   ↑
存储      localStorage / 坚果云
```

另外几个文件是「旁路」，谁需要谁调用：`exporter.js`（导出）、`pdf.js`（打印）、`importer.js`（导入）、`toast.js`（弹提示）。

| 文件 | 负责什么 |
|---|---|
| `js/config.js` | 各种固定值：四个象限的名称和颜色、存储位置的名称等 |
| `js/util.js` | 小工具：日期格式化、生成唯一编号、防止特殊字符捣乱 |
| `js/store.js` | **唯一的数据出入口**。读、写、备份、恢复全在这。内部同时管两个存储（localStorage 和安卓的 Preferences），对上层只暴露一套接口 |
| `js/render.js` | 把数据画到页面上。**只读数据，不改数据** |
| `js/task-ops.js` | 任务的增删改、勾选、统计已完成/总数/完成率 |
| `js/drag.js` | 鼠标拖着任务换位置、换象限 |
| `js/date-nav.js` | 日期选择器、切换日期 |
| `js/exporter.js` | 导出 JSON / Markdown / ZIP，以及 Ctrl+S 的处理 |
| `js/pdf.js` | 把内容打印成 PDF |
| `js/importer.js` | 导入 JSON 文件，检查格式、去掉重复 |
| `js/toast.js` | 所有提示信息的统一出口 |
| `js/theme.js` | 亮色 / 暗色主题的切换和记住 |
| `js/app.js` | 启动程序：把上面这些都初始化好，绑上按钮 |

### 1.4 脚本加载顺序

`index.html` 里引入这些 js 文件时，**顺序不能乱**，否则会报「找不到 XXX」的错。

```
config → util → store → toast → theme → render
→ task-ops → drag → date-nav
→ exporter → pdf → importer → app
```

记忆方法：**被依赖的排在前面**。`app.js` 要用所有东西，所以排最后。

### 1.5 程序启动时做了什么

打开网页后，程序依次执行这 8 步：

```
1. 读取数据          把本地的数据读出来
2. 应用主题          亮色还是暗色
3. 准备日期选择器     默认停在今天
4. 准备拖拽          让四个象限能接受拖进来的任务
5. 绑定按钮          添加 / 导入 / 导出 / 主题
6. 绑定快捷键        Ctrl+S 导出，Esc 取消编辑
7. 监听其他标签页     别的标签页改了数据，这边要能察觉
8. 画出页面          第一次渲染
```

**第 1 步如果出问题，程序不能直接崩掉**：要继续启动，并且明确告诉用户「数据读取异常」，而不是白屏或者悄悄用空数据把原来的覆盖掉。

### 1.6 一次操作从头到尾发生了什么

以「用户新增一个任务」为例，完整走一遍：

```
用户点「＋ 添加任务」，输入「写季度报告」
   ↓
task-ops.js 判断：文本去掉空格后是不是空的？是空的就拒绝
   ↓
生成一个新任务：给它一个唯一编号，completed 设为 false
   ↓
把这个任务放进当前日期、当前象限的列表里
   ↓
store.js 保存：写进 localStorage，顺手更新一份备份
   ↓
如果开了坚果云同步，改动攒一下再传上去（不是每改一个字就传一次）
   ↓
render.js 重新画页面
   ↓
用户看到任务出现在象限里
```

其他操作（勾选、拖拽、删除、改文字）都是同一个套路：**改数据 → 保存 → 重画**。

### 1.7 两条必须守住的规矩

这两条是防止以后代码越改越乱的关键。请写在最显眼的地方。

**规矩一：数据只能通过 `store.js` 读写。**

任何文件都不准自己去操作 localStorage，也不准自己去调 Capacitor 的存储插件。需要新数据时，在 `store.js` 里加一个函数，别的文件调用它。

「安卓端要同时写两份存储」这件事，只在 `store.js` 内部处理，上层代码不用知道——这正是把唯一入口收在 `store.js` 的好处。

> 为什么：一旦有文件绕过去自己读写，就会出现「有的地方存了、有的地方没存」或者「两边存的字段名不一样」，数据会悄悄丢。这类问题极难排查，因为程序不报错，只是数据不见了。

**规矩二：算出结果的部分，和画页面的部分，要分开写。**

`task-ops.js`（算）、`store.js`（存取）、`importer.js` 的检查和去重部分、`exporter.js` 生成 Markdown 的部分——这些**纯算逻辑**里不准出现 `window`、`document` 这些和页面绑定的东西。

> 为什么：分开之后，这些逻辑可以在 Node 里直接跑测试，不用打开浏览器。如果不分开，就只能靠手工点页面来检查，很容易漏——漏一次就是一个线上 bug。

### 1.8 建议的开发顺序

按依赖关系从下往上做，每一步做完都能验证：

```
第 1 步  config.js + util.js + store.js      能存能取，用 Node 测试验证
第 2 步  render.js + index.html + style.css  页面能画出空的四象限
第 3 步  task-ops.js                         能加任务、勾选、删除
第 4 步  drag.js + date-nav.js               能拖拽、能切日期
第 5 步  exporter.js + importer.js           能导出能导入
第 6 步  theme.js                            主题
第 7 步  pdf.js                              打印 PDF
第 8 步  打包成安卓 App + 接 Preferences     先在浏览器上做全功能，再打包
第 9 步  坚果云同步                          放最后，因为它最容易出问题
```

**每一步做完都跑一遍对应的测试**，不要攒到最后一起调。

### 1.9 网页版怎么发布

**决定：放到静态网站（GitHub Pages）上，用网址访问**（见 D-19）。不走「双击打开本地文件」这条路。

| 为什么选静态网站 | 说明 |
|---|---|
| 同步才做得成 | 双击打开时，页面发出的请求身份是「null」，坚果云几乎不会允许；放在 https 网站上才是正常的网址身份 |
| 下载、复制都正常 | 本地文件在部分浏览器里不算「安全环境」，下载和剪贴板会被限制 |
| 数据隔离干净 | 数据按网址存放，不同地址互不干扰 |

**一条必须记住的规矩：数据是跟网址绑死的。**

换网址（改仓库名、换域名、搬到别的托管），用户就再也读不到原来的数据了——数据其实还在浏览器里，只是新网址看不到。所以**网址定下来后不要随便改**；真要改，必须提前让用户导出 JSON 备份。

这和 D-14（安卓端的来源地址不能改）是**同一类问题**，两边都要守住。

**开发时不受影响**：本地开发照样可以双击 `index.html` 看效果，只是那个环境下同步用不了。这不碍事——同步本来就排在最后做（见 1.8 第 9 步）。

**更新是即时的**：本期不用 Service Worker，所以代码传上去之后，用户刷新一下就是新版本，不会出现「代码改了但用户还在跑旧版」的情况。

## 二、存储方案

### 2.1 数据存在哪里

每个用户的数据分三处放：

| 放在哪 | 放什么 | 什么时候用 |
|---|---|---|
| 浏览器本地 `localStorage` | 全部任务数据、4 份备份 | 网页版和 App 都用，日常读写都走这里 |
| 安卓原生存储（Capacitor Preferences） | 和上面同一份数据的副本 | **只有安卓 App 用**，防止系统把 localStorage 清掉 |
| 坚果云（可选） | 一个 JSON 文件 | 在两台设备之间传数据 |

**本地是主，云端是副本。** 没网的时候照样能用，数据先存在本地，联网后再传上去。

**为什么安卓端要多存一份**：安卓系统在存储空间紧张时，会回收 App 内置浏览器的 localStorage。这是官方写明的已知行为——Capacitor 文档说 localStorage「必须被视为临时的，你的 App 需要预期数据最终会丢失」。

网页版不受影响（浏览器不会清掉自己用户的网站数据），但安卓上如果只靠 localStorage，用户可能在毫无预兆的情况下丢掉全部数据。所以安卓端每次保存时，**同时再往系统自己的存储里写一份**。

两个存储的分工：

| 存储 | 作用 |
|---|---|
| `localStorage` | 日常读写走这里，快，网页版和 App 通用 |
| Capacitor Preferences | 保险。localStorage 读不出来时，从这里恢复 |

**注意：2.4 的 4 份滚动备份挡不住这种情况。** 那 4 份备份和主数据存在**同一个** localStorage 里，系统一清就是 5 份一起没。真正能挡住系统回收的，是 Preferences 这一份。

### 2.2 各个存储位置分别放什么

存储位置的名字（key）一旦写进用户设备就不能改了，改了等于数据全丢。

| 存储位置的名字 | 里面放什么 | 能删吗 |
|---|---|---|
| `quadrant_user_data:default` | **主数据**：所有日期的任务 | 绝对不能删 |
| `quadrant_user_data:default_backup` | 备份 1（最近一次） | 删了就失去一次恢复机会 |
| `quadrant_user_data:default_backup_1` | 备份 2 | 同上 |
| `quadrant_user_data:default_backup_2` | 备份 3 | 同上 |
| `quadrant_user_data:default_backup_3` | 备份 4（最旧） | 同上 |
| `quadrant_ui_theme` | 亮色还是暗色 | 可以删，删了回到亮色 |
| `quadrant_last_date` | 上次看的是哪天 | 可以删，删了回到今天 |

**名字里 `default` 是用户标识**。本期只有一个用户，所以固定是 `default`。这样写是为了将来真的做登录功能时，不用改结构，加个用户就是新增一组 key。

**主题不放进用户数据里。** 因为主题是「这台设备看着舒服」的设置，不该跟着数据同步到别的设备去。

**安卓 App 里还有一份额外副本**，存在 Capacitor Preferences 中，只用一个键（如 `quadrant_prefs_backup`）装整个 JSON，内容就是主数据的完整拷贝。

它不参与日常读写，只在一个时候派上用场：**打开 App 时如果发现 localStorage 是空的或读不出来，就自动从这份副本恢复**，恢复完明确告诉用户「已从本地副本恢复数据」。

判断「是不是真的丢了」要小心：新用户第一次打开时 localStorage 本来就是空的，不该弹恢复提示。所以要靠一个标记区分「从没存过」和「存过但现在没了」。

### 2.3 数据长什么样

主数据就是一个 JSON，结构很简单：

```json
{
  "user": "default",
  "dates": {
    "2026-10-01": {
      "I":   [ { "id": "id_1759_a1b2", "text": "写季度报告", "completed": false, "createdAt": 1759300000000 } ],
      "II":  [],
      "III": [],
      "IV":  []
    },
    "2026-10-02": { "I": [], "II": [], "III": [], "IV": [] }
  }
}
```

拆开看：

- `dates` 下面，**每个日期一个条目**，日期之间互相独立。改 10 月 1 号的内容，绝对不会影响 10 月 2 号。
- 每个日期下面固定有 `I` `II` `III` `IV` 四个列表，对应四个象限。
- **列表里的先后顺序，就是页面上从上到下的顺序。** 拖拽调整顺序时，实际就是把这个列表重新排一遍，不需要额外记「谁排第几」。

一个任务就四个字段：

| 字段 | 含义 |
|---|---|
| `id` | 唯一编号。用来区分「这是同一个任务」还是「这是两个不同的任务」 |
| `text` | 任务内容。**去掉首尾空格后不能是空的**，空的拒绝创建 |
| `completed` | 勾没勾上 |
| `createdAt` | 什么时候建的。出问题时方便排查 |

### 2.4 备份与自动恢复

**为什么要备份**：`localStorage` 里的数据只有一份。程序如果因为某个 bug 把数据写坏了，或者用户手滑，没备份就真的找不回来了。

**怎么做**：

- 每次保存数据时，**顺手把上一版往后挪一格**，一共留 4 个历史版本。最旧的那个被挤掉。
- 挪备份这件事**最多 30 秒做一次**。因为用户快速勾选时会连续保存，每次都挪一遍会产生一大堆没意义的备份，纯属浪费空间。

**数据读不出来时怎么办**：

```
读主数据 → 读失败
   ↓
挨个试 备份1 → 备份2 → 备份3 → 备份4
   ↓
试到哪个能读通，就用它把主数据恢复回去，并告诉用户
   ↓
四个备份全读不通
   ↓
不覆盖磁盘上的数据，用空数据先启动，明确提示用户「请导入备份文件」
```

**关键：不管成功还是失败，都要让用户看见。** 最糟糕的做法是读失败后悄悄返回一个空的，用户以为自己的数据被清空了，其实还在磁盘上——只是程序没告诉他。这种情况一定要弹提示。

**这套备份挡不住什么**：4 份备份和主数据在同一个 localStorage 里，所以它只防「程序把数据写坏了」，防不住「系统把整个 localStorage 清空」——那种情况下 5 份一起消失。挡后一种情况要靠 2.1 说的安卓原生存储副本，以及用户自己导出的 JSON 文件。

### 2.5 同步方案：坚果云 WebDAV

**做什么**：网页版和安卓 App 都直接读写坚果云上的**同一个 JSON 文件**。改完数据就传上去，打开时先拉下来。

**为什么这么选**：

- 用户拿自己的坚果云账号，我们**不用买服务器，也不用备案**
- 坚果云免费额度是每月 1G 上传 / 3G 下载、每 30 分钟 600 次请求，而我们传的就是几十 KB 的 JSON，完全够用
- WebDAV 是标准接口，网上资料多，出问题好查

**连接信息**：

| 项 | 值 |
|---|---|
| 服务器地址 | `https://dav.jianguoyun.com/dav/` |
| 用户名 | 用户自己的坚果云账号（首次使用时在 App 里填） |
| 密码 | 用户在坚果云后台生成的「应用密码」（首次使用时在 App 里填） |

> **不要把任何账号密码写进这份文档。** 文档可能会被分享、提交到代码仓库、发给别人看。正确的做法是：让用户在程序里首次配置时自己输入，然后只存在用户自己的设备上。如果是多人共用一份代码，更要在发布前检查一遍有没有把密码漏在文件里。

**同步时机**：

| 什么时候 | 做什么 |
|---|---|
| 用户改完数据 | 攒 3 秒再传（避免连续操作时反复上传） |
| 打开程序 | 先拉一次云端数据 |
| 手动点击 | 用户自己点「上传」或「下载」 |

**两台设备同时改怎么办**：本期采用**最后保存的赢**。也就是谁后传，云端就是谁的版本。这个取舍是明确的——真正的合并逻辑（逐条对比、有冲突时两边都留）实现复杂、出 bug 的风险高，本期不做。

**同步失败了怎么办**：**绝对不能影响本地使用**。数据本来就在本地好好的，传不上去只是暂时同步不了。提示用户「同步失败，数据已保存在本地」，等下次改动或手动点击时再传。

> **关于网页端的跨域**：网页版直接访问坚果云 WebDAV，可能被浏览器的**跨域限制**挡住——如果坚果云没有明确声明「允许网页访问」，浏览器会直接拦掉请求。安卓 App 不受这条限制（App 不走浏览器的安全规矩）。
>
> 已决定**按「可行」推进，不设前置验证关卡**（见 D-15）。写同步功能时顺手实测一次即可；万一实测不通，退路是：网页端只保留本地使用，同步功能只在 App 端提供。

### 2.6 导入与去重

导入就是选一个之前导出的 JSON 文件，把里面的数据并进来。

**检查格式，不合格就整个拒绝**：

```
读文件 → 内容不是合法的 JSON        → 拒绝，原数据一点不动，提示「文件格式有误」
       → 不是数据对象               → 拒绝，提示具体哪里不对
       → 缺少象限列表               → 拒绝，提示具体哪里不对
       → 日期格式不对               → 拒绝，提示具体哪里不对
       → 全部检查通过               → 才开始合并
```

**先全部检查完，确认没问题，再写数据。** 不能边读边写——中途发现有问题时，已经写进去的那部分就留在里面了，数据会变得半新半旧。

**怎么算重复**：如果一个任务的**象限**和**文本内容**都一样，就认为是同一个任务，跳过不插入。判断用「内容」而不是用「编号」——因为同一个任务在两台设备上各自创建时，会拿到两个不同的编号，靠编号判断的话会重复插入一堆一样的任务。

**导入后要告诉用户结果**：比如「新增 12 条，跳过 3 条」。不然用户不知道导入到底成没成功。

**已确定：不看勾选状态**（见 D-16）。文本相同就算同一个任务；跳过后**保留本地已有的勾选状态**，不被文件里的状态覆盖。

### 2.7 导出格式

| 格式 | 内容 | 用途 |
|---|---|---|
| `.json` | 主数据全量 | **唯一能重新导入回去的格式**，最重要的备份 |
| `.md` | 按日期排好的四象限文本 | 存档、也用来生成 PDF |
| `.pdf` | 由 `.md` 打印而来（见 4.4） | 阅读、打印、发给别人 |
| `.zip` | 上面三种打包成一个文件 | 手机上一键保存全部格式 |

导出的文件里**不含主题设置**，因为主题是本机偏好，不是数据。

**zip 里固定就是这三种格式**（JSON + Markdown + PDF），不做按需勾选（见 D-18）。

## 三、测试策略

### 3.1 分成三层

| 层 | 怎么做 | 检查什么 | 什么时候做 |
|---|---|---|---|
| 自动测试 | Node 脚本 | 算数据的逻辑：存取、导入检查、排序、统计、日期 | 每次改完对应代码 |

### 3.2 自动测试清单

放在 `test/` 文件夹，每个文件直接跑 `node test/文件名.js` 就行。跑出来有问题会直接打印出来。

| 文件 | 检查什么 |
|---|---|
| `test-util-date.js` | 日期处理；重点查跨月跨年，别出现 `2026-13-01` 这种错误日期 |
| `test-store-serialize.js` | 存进去再读出来对不对；空日期要返回空列表；备份轮转和 30 秒限流是否生效 |

| `test-import-validate.js` | 各种格式不对的文件，是不是都被拒绝、且原数据一点没动 |
| `test-import-merge.js` | 去重规则：同象限同文本跳过、不同象限的相同文本保留 |

### 3.3 手工验收清单

照着点一遍，每条都要实际验证过才算完成。

**核心功能**

- 第一次打开：默认停在今天，四个象限是空的，页面没有报错
- 刷新页面：任务内容、勾选状态、排列顺序都还在
- 打开一个没数据的日期：显示空状态，不报错
- 输入空任务：拒绝创建，并给出提示
- 输入很长的任务：能自动换行完整显示，手机上不溢出、不截断
- 日期隔离：改 10 月 1 号的任务，10 月 2 号的没变化
- 日期边界：跨月、跨年切换正常
- 拖拽：同象限换顺序、拖到别的象限，都生效，刷新后还在
- 勾选：完成的任务有删除线、颜色变淡，顶部统计跟着变
- 手机上（窄屏）：变成 1 列 4 行，添加/勾选/编辑/删除/拖拽都能用，按钮不会小到点不准
- 任务多的时候：一天 200 条也不卡死、不丢数据
- 主题：亮暗能切，刷新后记得住；导出文件里不含主题设置

**次要功能**

- 导出 JSON：文件能下载，而且能重新导入回来
- 导出 Markdown / PDF：内容和当前页面上的数据一致
- 电脑上按 Ctrl+S：三种格式都能下载
- 手机上导出：能选格式，包括打包成 zip；zip 用手机自带解压能打开
- 导入：正常文件合并成功并显示「新增几条、跳过几条」；格式错的文件被拒绝且原数据不变
- 导入前有二次确认，并提示「建议先导出备份」

**两台设备之间**

- 电脑导出 JSON → 手机导入 → 数据一致
- 手机导出 JSON → 电脑导入 → 数据一致
- 两边各加了任务后互相导入 → 按「象限+文本」判重，没有重复条目

**同步（如果做了坚果云）**

- 电脑改完 → 手机打开能看到
- 两台设备一起改同一个任务 → 后改的赢，不报错
- 断网时改数据 → 本地正常用 → 联网后能传上去
- 同步失败 → 本地数据完好，有明确提示

**安卓端的数据安全**

- 正常关掉 App 再打开：数据还在
- 重启手机再打开：数据还在
- 在设置里「清除缓存」：数据不受影响（这是数据，不是缓存）
- 手动把 localStorage 清空后打开 App：能提示从本地副本恢复，数据救得回来
- 第一次装 App（从没存过数据）：正常显示空状态，**不弹恢复提示**
- 卸载重装：数据确实没了（属于预期），但提示里应引导用户用导出的 JSON 导入

**开两个标签页**

- 标签 A 改了数据，标签 B 刷新后能看到
- 两边同时改，以最后保存的为准

| 改了 | 必须重跑 |
|---|---|
| `store.js` | `test-store-serialize` / `test-store-recovery` |
| `importer.js` | `test-import-validate` / `test-import-merge` |

## 四、错误处理

### 4.1 错误分四级

| 级别 | 什么情况 | 怎么处理 |
|---|---|---|
| **严重** | 可能把数据弄坏或弄丢 | 停止这次操作，明确提示，引导用户先导出备份 |
| **重要** | 这次操作失败，但数据没事 | 拒绝操作，保住原数据，说明原因 |
| **一般** | 功能没做成，影响不大 | 换个方式凑合，轻提示一下 |
| **不用管** | 用户完全感知不到 | 只在后台记一笔，不打扰用户 |

### 4.2 常见错误怎么处理

| 出什么事 | 级别 | 怎么处理 | 用户看到什么 |
|---|---|---|---|
| 存储空间满了 | 严重 | 这次保存不算数，退回到改动前的状态 | 「存储空间不足，本次修改未保存。请导出备份并清理历史日期。」 |
| 数据读坏了，但备份能救 | 严重 | 自动从最近的可用备份恢复 | 「数据异常，已从备份恢复到 X 月 X 日 X 点的版本。」 |
| 数据丢了备份也救不回来 | 严重 | 用空数据启动，**但不覆盖磁盘上的原文件** | 「数据无法读取。请先别继续操作，导入本地备份文件。」 |
| 导入的文件不是合法 JSON | 重要 | 拒绝导入，原数据一点不动 | 「文件格式有误，导入已取消。」 |
| 导入的文件结构不对 | 重要 | 拒绝导入，原数据一点不动 | 指出具体是哪个字段不对 |
| 任务内容是空的 | 一般 | 拒绝创建 | 「任务内容不能为空。」 |
| 下载被浏览器拦了 | 一般 | 改成弹窗把内容显示出来让用户复制 | 「下载被拦截，请手动复制内容。」 |
| 这台设备不支持打印 | 一般 | 改成把 Markdown 文本显示出来让用户复制 | 「当前环境无法打印，已提供 Markdown 文本。」 |
| 主题设置读不出来 | 不用管 | 用默认的亮色 | 无 |
| 上次看的日期读不出来 | 不用管 | 用今天 | 无 |

### 4.3 所有提示走同一个出口

**所有给用户看的提示，都必须通过 `toast.js` 弹出来。** 不准直接用浏览器自带的弹窗，也不准只在后台打印一行日志就算完。

理由：

- 浏览器自带弹窗在手机上样式很丑，而且会卡住整个页面
- 只在后台打日志等于**没提示**——用户根本看不到，只会觉得「我点了没反应」。以前就吃过这个亏：数据同步一直在悄悄失败，用户完全不知道，等发现时已经丢了很多改动

提示分三种：成功、警告、错误。**错误的提示至少停留 5 秒**，别让用户还没看清就消失了。

### 4.4 PDF 导出的做法

**思路：先把内容排成 Markdown，再让浏览器把它打印成 PDF。**

```
数据 → 生成 Markdown 文本 ─┬─ 存成 .md 文件
                            └─ 变成网页 → 套上打印专用样式 → 交给浏览器打印成 PDF
```

**为什么绕这一圈**：Markdown 和 PDF 用的是同一份内容。如果两种格式各写一套排版代码，将来改了任务显示格式，很容易只改了一处、忘了另一处，导出的两种文件就对不上了。

**打印专用样式**要单独写一段，规则是：

- 把所有按钮、工具栏藏起来（打印出来不该有按钮）
- 象限的彩色背景去掉，改用边框区分（省墨水、也更清楚）
- 保证黑白打印也能看清
- 一条任务尽量不跨页断开

**要提前告诉用户的两件事**：

1. 最终 PDF 是浏览器或系统生成的，**不同浏览器、不同电脑上排版会有细微差别**（字体、边距、分页位置）。不要承诺「每次导出都一模一样」。
2. 手机上导出 PDF 会弹出系统的打印窗口，需要用户自己确认一下。

如果某台设备根本不能打印（部分 App 内置浏览器），就退一步：把 Markdown 文本显示出来让用户复制。

## 五、风险与决策记录

### 5.1 已经定下来的决定

这些是已经拍板的，改之前要先改这份文档并说明理由。

| 编号 | 决定 | 为什么这么定 |
|---|---|---|
| D-01 | 同步用坚果云 WebDAV | 用户自带账号，不用买服务器、不用备案；JSON 只有几十 KB，免费额度绰绰有余 |
| D-02 | 同步冲突采用「最后保存的赢」 | 真正的逐条合并实现复杂、出错概率高，本期不做 |
| D-03 | 测试用 Node 脚本 + 手工清单 | 不装任何东西就能跑，符合「不引入第三方库」 |
| D-04 | PDF 从 Markdown 导出 | 两种格式共用一份内容，不会对不上 |
| D-05 | 全部代码自己写，不用任何第三方库 | 不会因为别人更新库而突然坏掉；出问题好查 |
| D-06 | 所有日期数据存在一个地方 | 导出、导入、备份、恢复都只处理一个文件，简单 |
| D-07 | 存储位置带用户标识（`default`） | 将来真做登录时不用改结构 |
| D-08 | 留 4 份备份，最多 30 秒轮换一次 | 数据坏了能救回来；限制频率避免产生一堆无用的备份 |
| D-09 | 判重按「象限 + 文本」，不按编号 | 同一个任务在两台设备上创建会得到不同编号，按编号判重会重复插入 |
| D-10 | 任务顺序由列表的先后决定，不额外记「排第几」 | 拖拽时直接重排列表就行，少维护一个字段 |
| D-11 | 主题不放进数据里，单独存 | 主题是本机偏好，不该同步到别的设备 |
| D-12 | 算逻辑的代码和画页面的代码分开写 | 分开了才能自动测试；上一版就是因为混在一起，只能手工点，漏了十几处问题 |
| D-13 | 安卓端额外用 Capacitor Preferences 存一份副本 | 安卓系统会在存储紧张时回收 localStorage，只靠它会无声丢掉全部数据 |
| D-14 | Capacitor 的来源地址（scheme）定下后写死，永不更改 | 来源变了等于换了域名，老用户的 localStorage 会读不到，看起来就像数据丢了 |
| D-15 | 网页端同步按「可行」推进，不设前置验证关卡 | 判断跨域大概率可行；验证成本低，留到写同步功能时顺手实测 |
| D-16 | 导入判重不看勾选状态 | 同象限同文本就是同一条任务；不覆盖本地已有的状态 |
| D-17 | 安卓端发现数据丢失时**自动恢复** | 少一步操作；恢复后明确告知用户即可 |
| D-18 | 打包 zip 固定为 JSON + Markdown + PDF 三件套 | 不做组合勾选，交互简单、实现也简单 |
| D-19 | 网页版发布到静态网站（GitHub Pages），不做「双击打开本地文件」路线 | 同步需要正常的网址身份；本地文件环境下下载和剪贴板也受限 |
| D-20 | 本期不做旧数据迁移 | 这是从零开始的项目，没有代码、没有任何历史数据，没有可迁移的对象 |

### 5.2 需要注意的风险

| 编号 | 风险 | 会有什么后果 | 怎么防 |
|---|---|---|---|
| R-01 | **网页版可能连不上坚果云**（跨域限制） | 网页端的同步功能完全用不了 | 已决定按可行推进（D-15）。写同步时实测一次；万一不通，退路是同步只在 App 端做，或换一个支持跨域的服务 |
| R-02 | **账号密码被写进文档或代码里** | 账号被盗用 | 密码只让用户在程序里填、只存在他自己设备上；发布前检查一遍有没有漏 |
| R-03 | 两台设备同时改 | 后改的覆盖先改的，先改的丢失 | 已经声明为已知限制；界面上说清楚，让用户知道别同时改 |
| R-04 | 存储空间占满 | 当次修改保存不上 | 占用超过 80% 就提醒用户导出备份、清理旧日期 |
| R-05 | PDF 在不同设备上排版不一样 | 用户觉得「怎么和上次不一样」 | 只承诺内容对、能看清，不承诺排版完全一致 |
| R-06 | 手机上没有 Ctrl+S 快捷键 | 导出方式和电脑不一样 | 手机上改成手动点选格式，并支持打包 zip |
| R-07 | 一天 200 条任务时页面卡 | 操作卡顿 | 连续操作时攒一下再重画；按时验收 |
| R-08 | 规矩靠人自觉遵守 | 以后有人绕开 `store.js` 直接读写，重复上一版的数据丢失问题 | 1.7 的两条规矩写在最显眼处，改代码时优先检查 |
| R-09 | 用户以为两台设备会自动一致 | 两边各改各的，产生困惑 | 界面上明确写「同步需要手动点上传/下载」或者说明同步时机 |
| R-10 | **安卓系统回收 localStorage** | 用户毫无预兆地丢掉全部数据，连 4 份滚动备份一起丢 | 每次保存同时写一份到 Capacitor Preferences；启动时发现数据没了就**自动恢复**（D-17） |
| R-11 | **Capacitor 升级改了来源地址**（6.0 把默认值从 http 改成了 https） | 老用户升级后读不到数据，看起来像丢了 | 在 Capacitor 配置里把来源写死；升级前先验证老数据仍在 |
| R-12 | **网页版换网址** | 老网址下的数据读不到，看起来像丢了 | 网址定下后不改；确需更换时，提前让用户导出 JSON 备份（与 D-14 是同一类问题） |
