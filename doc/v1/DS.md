## 先看懂这几个词

后面会反复用到，先解释一遍。已经懂的话可以跳过。

| 词 | 大白话解释 |
|---|---|
| **localStorage** | 浏览器自带的一个小仓库。网页把数据存在这里，关掉浏览器再打开还在。同一台设备、同一个浏览器，就有这一份。 |
| **Capacitor Preferences** | Capacitor 官方提供的存储插件。安卓上它落在系统的 SharedPreferences 里，比 localStorage 稳当——只有卸载 App 才会清掉。 |
| **JSON** | 一种把数据写成文本的格式。长这样：`{ "text": "写报告", "completed": false }`。因为是人能看懂的文本，所以很适合用来做备份文件。 |
| **四象限** | 把任务按「重要 / 紧急」两个维度分成四类：I 重要且紧急、II 重要不紧急、III 紧急不重要、IV 都不占。 |
| **Markdown（.md）** | 一种用纯文本排版的格式。`# 标题`、`- 列表` 这样写，看起来还是普通文字，但能转成好看的样式。 |
| **PDF** | 排版固定、到哪台设备上看起来都一样的文档格式。 |
| **WebDAV** | 一种「网盘的标准接口」。用它可以像操作文件夹一样操作网盘上的文件，不用自己写服务器程序。 |
| **跨域（CORS）** | 浏览器的安全规矩：网页 A 想访问网站 B 的接口，如果网站 B 没明确说「允许」，浏览器就会拦下来。**这条规矩只拦网页，不拦手机 App**，后面会重点提到。 |
| **备份** | 把数据多留几份。万一手滑删了、或者程序出错把数据写坏了，还能从旧的副本找回来。 |

## 一、技术栈与模块划分

### 1.1 用什么技术

| 部分 | 选择 | 为什么 |
|---|---|---|
| 页面 | 一个 `index.html` | 没有构建步骤，本地双击就能看效果（正式发布见 1.9） |
| 样式 | 一个 `css/style.css` | 全部外观集中在一处，好改 |
| 代码 | 原生 JavaScript（不用框架） | 不装任何第三方库，也就不会因为库升级而坏掉 |
| 本地存储 | 浏览器自带的 localStorage | 不用买服务器，数据就在用户自己设备上 |
| 安卓端的额外保险 | Capacitor Preferences（官方插件） | 安卓系统会回收 localStorage，见 2.1 |
| 打包成 App | Capacitor | 把网页包成安卓 App |
| 测试 | Node 脚本 | 不装任何东西就能跑 |

**一条总原则：页面运行时尽量不引入任何第三方代码库。** 不用 React / Vue，不用 jQuery，页面里不用 npm 装包。页面代码全部是我们自己写的，出问题好查，也不会因为别人更新了库而突然跑不动。

> **本版（v1）不包含云端同步。** 跨设备靠「导出 JSON → 手动导进去」，不依赖任何服务器或第三方服务。所有同步相关的设计、实测结论和风险，全部集中在第六章，本版不实现。这条边界很重要——**第五章之后的内容，读到这里就可以先不管了**。

**例外一｜打包安卓 App 绕不开第三方工具。** Capacitor 本体、`@capacitor/preferences` 插件，以及安卓构建链（Gradle / Android SDK），都必须通过 npm 安装，会在仓库里生成 `node_modules/` 和 `android/` 目录。这属于**构建期依赖**，和「页面运行时不引第三方库」不冲突。第 8 步打包之前，这些东西一个都不需要。

**例外二｜真到了非用不可的时候，可以用。** 判断标准是「自己写不划算，或者自己写风险更高」。但**不许悄悄引入**——用了什么、为什么用、考虑过哪些替代方案，必须登记到本文档 5.1 的决策表里。

**为什么要留这个口子**：把「一律不准用」写死，将来遇到一个必须用库才能做对的功能时，后来者只有两条路——违反文档硬写一个容易出错的实现，或者卡住不动。两条都是坏结果。

### 1.3 每个文件负责什么

代码按「谁不依赖谁」分成几层。这样分的好处是：改上面一层不会影响下面一层。

```
入口层    app.js                          程序从这里启动
   ↑
交互层    drag.js（拖拽） date-nav.js（切日期） theme.js（主题）
业务层    task-ops.js（增删改勾选）
   ↑
渲染层    render.js                        把数据画成页面
   ↑
数据层    store.js                         读写数据，只此一家
   ↑
存储      localStorage（本版只有本地，没有云）
```

另外几个文件是「旁路」，谁需要谁调用：`exporter.js`（导出）、`pdf.js`（打印）、`importer.js`（导入）、`toast.js`（弹提示）。

| 文件 | 负责什么 |
|---|---|
| `js/config.js` | 各种固定值：四个象限的名称和颜色、存储位置的名称等 |
| `js/util.js` | 小工具：日期格式化、生成唯一编号、防止特殊字符捣乱 |
| `js/store.js` | **唯一的数据出入口**。读、写、备份、恢复、30 天归档的裁剪判断全在这。内部同时管两个存储（localStorage 和安卓的 Preferences），对上层只暴露一套接口 |
| `js/prefs.js` | 安卓原生存储（Capacitor Preferences）的适配器。**存在的理由**：Preferences 是异步的，而 `store.js` 通篇是同步的（它得能在 Node 里简单地测）。这个文件把异步收口在一处，给 store 一个同步的壳。网页版里它整个是空操作 |
| `js/render.js` | 把数据画到页面上。**只读数据，不改数据** |
| `js/task-ops.js` | 任务的增删改、勾选、统计已完成/总数/完成率。**阶段的增删改、排序、进度计算也在这**（见 2.9）——`getProgress` 是全项目算进度的唯一一份实现。v1.1 起**任务块与计划池、模板的增删改查也在这**（见 2.10、2.11、2.14）：它们都只是「数据换了形状，操作还是那几样」 |
| `js/drag.js` | 拖着任务换位置、换象限。**鼠标和手指都要支持**——用 Pointer Events 统一处理，不能只用 HTML5 拖拽（见 D-26）。它只负责「接住指针」和「算出落点」；**真正挪数据的是 `task-ops.js` 的 `moveTask` / `moveItem`**，拖拽这里不碰数据。v1.1 起可拖对象有三种：阶段、任务、任务块（判定顺序见 2.10） |
| `js/date-nav.js` | 日期选择器、切换日期 |
| `js/exporter.js` | 导出 JSON / Markdown / ZIP、触发 30 天归档的下载，以及 Ctrl+S 的处理。**ZIP 是自己手写的**（没引第三方压缩库，见 D-05），压缩方式用「存储」——不压缩、原样塞进去 |
| `js/pdf.js` | 把内容打印成 PDF（**仅网页版**，见 4.4） |
| `js/importer.js` | 导入 JSON 文件，检查格式、去掉重复 |
| `js/toast.js` | 所有提示信息的统一出口 |
| `js/theme.js` | 亮色 / 暗色主题的切换和记住 |
| `js/app.js` | 启动程序：把上面这些都初始化好，绑上按钮 |

### 1.4 脚本加载顺序

`index.html` 里引入这些 js 文件时，**顺序不能乱**，否则会报「找不到 XXX」的错。

```
config → util → store → prefs → toast → render → theme
→ task-ops → drag → date-nav
→ exporter → pdf → importer → app
```

记忆方法：**被依赖的排在前面**。`app.js` 要用所有东西，所以排最后。

> **这份顺序被写错过一次，代价是整个页面白屏。**
>
> 当时把 `theme` 排在 `render` 前面，而 `theme.js` 是调 `Render.setTheme()` 去改主题的。于是它加载时 `Render` 还不存在，脚本末尾那句兜底
> `typeof Render !== 'undefined' ? Render : require('./render.js')` 就落到了 `require` 那一半——**浏览器里没有 `require`，直接抛错**。
>
> 后果的链条是这样的：`theme.js` 当场阵亡 → `Theme` 这个全局变量根本没被创建 → `app.js` 找不到它、同样抛错 → **`boot()` 一次都没跑，四个象限一个都不出来**。而控制台里只有一句「require is not defined」，完全指不到真正的原因。
>
> 现在 `test-load-order.js` 会盯着这件事：它既静态检查「每个文件依赖的东西是不是排在它前面」，也**按这个顺序在一个没有 `module` 的环境里真跑一遍**，还会确认 12 个全局变量最后都在。

### 1.5 程序启动时做了什么

打开网页后，程序依次执行这 8 步：

```
1. 读取数据          把本地的数据读出来
2. 应用主题          亮色还是暗色（真正抢先的是 <head> 里那段防闪白脚本，见 1.7）
3. 准备日期选择器     默认停在今天
4. 准备拖拽          让四个象限能接受拖进来的任务
5. 绑定按钮          添加 / 导入 / 导出 / 主题
6. 绑定快捷键        Ctrl+S 导出，Esc 取消编辑
7. 监听其他标签页     别的标签页改了数据，这边要能察觉
8. 画出页面          第一次渲染
```

**第 1 步如果出问题，程序不能直接崩掉**：要继续启动，并且明确告诉用户「数据读取异常」，而不是白屏或者悄悄用空数据把原来的覆盖掉。

读数据失败时的完整处理见 2.4：程序会进入**保护模式**——空四象限照常显示，但禁止一切写操作，磁盘上的原始数据一个字节都不动，由用户自己决定下一步（导入备份文件 / 用空数据重新开始）。

### 1.6 一次操作从头到尾发生了什么

以「用户新增一个任务」为例，完整走一遍：

```
用户点象限右上角的「＋」，输入「写季度报告」
   ↓
task-ops.js 判断：文本去掉空格后是不是空的？是空的就拒绝
   ↓
生成一个新任务：给它一个唯一编号，completed 设为 false
   ↓
把这个任务放进当前日期、当前象限的列表里
   ↓
store.js 保存：写进 localStorage，顺手更新一份备份
   ↓
安卓端：再写一份进 Capacitor Preferences（攒 3 秒写一次，见 2.2）
   ↓
每次保存后还要检查一次：本地数据跨度超过 30 天了没？超了就触发归档
   ↓
render.js 重新画页面
   ↓
用户看到任务出现在象限里
```

**编辑是在原地发生的**（见 D-31）：点象限右上角的「＋」，列表末尾长出一个输入框；点任务文字，那一条直接变成输入框。回车或点到别处提交，Esc 取消。**全程不弹对话框。**

其他操作（勾选、拖拽、删除、改文字）都是同一个套路：**改数据 → 保存 → 重画**。

**一个实现上的坑**：回车提交和失焦提交会撞车——按回车时，浏览器紧接着还会补一次失焦事件。所以提交函数一进门就把「正在编辑」的状态清掉，第二次调用会直接返回。另外，用户点别的地方时，那次点击要先正常处理完，失焦提交才轮到，所以它是延后一个事件循环执行的；执行前还要确认那个输入框是不是还在页面上（不在就说明点别处的动作已经重画过了，不必再提交）。

### 1.7 两条必须守住的规矩

这两条是防止以后代码越改越乱的关键。请写在最显眼的地方。

**规矩一：数据只能通过 `store.js` 读写。**

任何文件都不准自己去操作 localStorage，也不准自己去调 Capacitor 的存储插件。需要新数据时，在 `store.js` 里加一个函数，别的文件调用它。

「安卓端要同时写两份存储」这件事，只在 `store.js` 内部处理，上层代码不用知道——这正是把唯一入口收在 `store.js` 的好处。

> 为什么：一旦有文件绕过去自己读写，就会出现「有的地方存了、有的地方没存」或者「两边存的字段名不一样」，数据会悄悄丢。这类问题极难排查，因为程序不报错，只是数据不见了。

#### 规矩一的唯一一处例外：防闪白

`index.html` 的 `<head>` 里有一段内联脚本，会**直接读一次** localStorage。这是全项目唯一绕过 `store.js` 的地方。

**为什么非绕不可**：主题必须在 CSS 生效之前挂到 `<html>` 上。要等 body 末尾的 JS（其中才有 `store.js`）加载完再切的话，暗色用户会先看到一下白底、再闪成暗的——网络慢的时候这一下非常明显。

**为什么这么小的例外可以接受**：它被三条约束锁死了，少任何一条都不成立。

| 约束 | 说明 |
|---|---|
| **只读** | 一个字节都不写 |
| **只读主题这一个 key** | 不碰主数据、不碰任何用户数据 |
| **只做一件事** | 挂上 `data-theme`，读失败就静默用亮色 |

尤其注意第二条——**「只读用户数据」等于把唯一入口拆了**，不在这条例外的范围内。以后有人想往这段脚本里加点别的，先回来把这段读一遍。

> 代价：`quadrant_ui_theme` 这个名字在两处各写了一遍（`config.js` 和 `index.html`）。两处都留了互指的注释，改的时候一起改。

**规矩二：算出结果的部分，和画页面的部分，要分开写。**

`task-ops.js`（算）、`store.js`（存取）、`importer.js` 的检查和去重部分、`exporter.js` 生成 Markdown 的部分——这些**纯算逻辑**里不准出现 `window`、`document` 这些和页面绑定的东西。

> 为什么：分开之后，这些逻辑可以在 Node 里直接跑测试，不用打开浏览器。如果不分开，就只能靠手工点页面来检查，很容易漏——漏一次就是一个线上 bug。

### 1.8 建议的开发顺序

按依赖关系从下往上做，每一步做完都能验证：

```
第 1 步  config.js + util.js + store.js      能存能取，用 Node 测试验证   ✅ 已完成
第 2 步  render.js + index.html + style.css  页面能画出空的四象限        ✅ 已完成（移动端未验）
第 3 步  task-ops.js + toast.js              能加任务、勾选、改字、删除    ✅ 已完成
第 4 步  drag.js + date-nav.js               能拖拽、能切日期              ✅ 已完成（触摸拖拽未验）
第 5 步  exporter.js + importer.js           能导出能导入、30 天归档能跑通  ✅ 已完成
第 6 步  theme.js                            主题                          ✅ 已完成
第 7 步  pdf.js                              打印 PDF（仅网页版，见 4.4）  ✅ 已完成
第 8 步  打包成安卓 App + 接 Preferences     先在浏览器上做全功能，再打包   ⚠️ 配置已写好，但没验证过
```

**每一步做完都跑一遍对应的测试**，不要攒到最后一起调。

**第 8 步为什么放最后**：前 7 步全部能在浏览器里做完、验完，打包成 App 只是把已经跑通的东西换个壳。顺序反过来，每改一行都要重新打包才能看到效果，慢十倍。

**云端同步不在这张表里**——本版不做，见第六章。

### 1.9 网页版怎么发布

**决定：放到静态网站（GitHub Pages）上，用网址访问**（见 D-19）。不走「双击打开本地文件」这条路。

| 为什么选静态网站 | 说明 |
|---|---|
| 下载、复制都正常 | 本地文件在部分浏览器里不算「安全环境」，下载和剪贴板会被限制 |
| 数据隔离干净 | 数据按网址存放，不同地址互不干扰 |

> **一条已更正过的旧理由（存档）**：早期版本把「同步才做得成」列为选静态网站的头号理由，说「放在 https 网站上才是正常的网址身份」——**这条是错的**。跨域限制由**目标服务端**决定，跟我们自己的网址是 `file://` 还是 `https://` 没有任何关系。这段经历连同完整分析放在第六章。

**一条必须记住的规矩：数据是跟网址绑死的。**

换网址（改仓库名、换域名、搬到别的托管），用户就再也读不到原来的数据了——数据其实还在浏览器里，只是新网址看不到。所以**网址定下来后不要随便改**；真要改，必须提前让用户导出 JSON 备份。

这和 D-14（安卓端的来源地址不能改）是**同一类问题**，两边都要守住。

**开发时不受影响**：本地开发可以双击 `index.html` 看效果，也可以在正式网址上看。数据是跟网址绑的，所以**开发时用的网址和正式发布后的网址如果不一样，数据不互通**——这正好说明了下面这条规矩有多重要。

**更新是即时的**：本期不用 Service Worker，所以代码传上去之后，用户刷新一下就是新版本，不会出现「代码改了但用户还在跑旧版」的情况。

### 1.10 怎么打包成安卓 App

**开发时这些一样都不需要**（见 1.8 第 8 步），只有真要出 APK 的时候才用得上。

**先装这三样**：

| 要装的 | 为什么 |
|---|---|
| **JDK 17 或更新** | Gradle 要它才能编译安卓工程 |
| **Android SDK** | 装 Android Studio 最省事 —— SDK、模拟器、构建工具它都带 |
| Node | 已经有（跑 `npm` 用） |

**然后四条命令**：

```
npm install            # 装 Capacitor 本体、安卓平台、Preferences 插件
npm run sync:web       # 把页面拷进 www/（为什么不直接拷根目录，见 tools/copy-web.js 开头的说明）
npx cap add android    # 生成 android/ 工程 —— 只做一次
npm run android:open   # 日常就这一条：拷页面 → 同步 → 打开 Android Studio
```

在 Android Studio 里点 Run，就能装到手机或模拟器上。

**装依赖之前先看一眼版本**：`package.json` 里写的是 `^6.0.0`。跑一下 `npm view @capacitor/core version` 看现在最新是哪个大版本 —— 如果已经是 7.x 或更高，按官方的升级说明走，**并且特别注意下面 R-11 那条**。

**三条必须知道的**：

1. **`androidScheme` 已经在 `capacitor.config.json` 里写死成 `https`**（见 D-14）。**永远不要改它**——它决定 App 里那个网页的「来源」，改了等于换了域名，老用户的 localStorage 会读不到，看起来就像数据全丢了。
2. **Capacitor 升级时可能偷偷改这个默认值**（6.0 就把默认从 http 改成了 https，见 R-11）。所以每次升级 Capacitor 之前，先在真机上确认老数据还在，再往后走。
3. **安卓系统会回收 localStorage**（见 2.1）。这正是 `js/prefs.js` 存在的理由：每次保存时额外往系统存储里写一份，localStorage 空掉时从它恢复。

> ⚠️ **这一节没有被验证过。**
>
> 写这份文档的机器上**没有装 JDK，也没有 Android SDK**，所以上面这些命令**一条都没跑过**。`capacitor.config.json` 和 `js/prefs.js` 是照着 Capacitor 6 的接口写的，逻辑上自洽、也有测试兜着网页版那一半，但**没有经过任何真实的打包验证**。
>
> 第一次打包时如果哪里对不上，**以官方文档为准**，然后回来把这一节改对 —— 别让它以「写得很确定、其实是猜的」的样子留在文档里。

## 二、存储方案

### 2.1 数据存在哪里

每个用户的数据分三处放，**全部在用户自己的设备上，没有第四处**：

| 放在哪 | 放什么 | 什么时候用 |
|---|---|---|
| 浏览器本地 `localStorage` | **最近 30 天**的任务数据、4 份备份 | 网页版和 App 都用，日常读写都走这里 |
| 用户自己的磁盘（下载目录） | 超过 30 天的那部分历史，存成归档 JSON | 本地攒满 30 天后自动导出，见 2.4 |
| 安卓原生存储（Capacitor Preferences） | 和 `localStorage` 同一份数据的副本 | **只有安卓 App 用**，防止系统把 localStorage 清掉 |

**本版没有云端。** 数据只存在用户自己的设备里，不经任何服务器。跨设备怎么办？**导出 JSON，在另一台设备上导进去**（见 2.5、2.6）。这条路不需要联网、不需要账号、不需要任何第三方服务，代价是得手动操作一下。

> 云端自动同步是**下一版**的事，所有相关设计都已经写好、放在第六章，本版不实现。

**本地为什么只留 30 天**：`localStorage` 每个网站只有约 5MB，而我们还要在里面放 4 份备份——等于存 1 天的数据占了 5 天的地。如果本地无上限地累积，用不了几个月就会写满；写满之后**新的修改直接存不进去**，用户会看到「存储空间不足，本次修改未保存」。所以本地只留一个 30 天的滚动窗口，更早的数据自动导出成 JSON 落到用户自己的磁盘上（见 2.4）。

**代价，必须让用户知道**：本地只留 30 天，意味着**想回看更早的数据，得手动把归档的 JSON 导回来**。这句话要出现在界面的归档提示里，不能让用户以为数据丢了。

**为什么安卓端要多存一份**：安卓系统在存储空间紧张时，会回收 App 内置浏览器的 localStorage。这是官方写明的已知行为——Capacitor 文档说 localStorage「必须被视为临时的，你的 App 需要预期数据最终会丢失」。

网页版不受影响（浏览器不会清掉自己用户的网站数据），但安卓上如果只靠 localStorage，用户可能在毫无预兆的情况下丢掉全部数据。所以安卓端在每次保存之后，**额外再往系统自己的存储里写一份**——攒 3 秒写一次，不是每敲一个字写一次（见 2.2）。

两个存储的分工：

| 存储 | 作用 |
|---|---|
| `localStorage` | 日常读写走这里，快，网页版和 App 通用 |
| Capacitor Preferences | 保险。localStorage 读不出来时，从这里恢复 |

**注意：2.4 的 4 份滚动备份挡不住这种情况。** 那 4 份备份和主数据存在**同一个** localStorage 里，系统一清就是 5 份一起没。真正能挡住系统回收的，是 Preferences 这一份。

### 2.2 各个存储位置分别放什么

存储位置的名字（key）一旦写进用户设备就不能改了，改了等于数据全丢。

| 存储位置的名字 | 里面放什么 | 能删吗 |
|---|---|---|
| `quadrant_user_data:default` | **主数据**：最近 30 天的任务 | 绝对不能删 |
| `quadrant_user_data:default_backup` | 备份 1（最近一次） | 删了就失去一次恢复机会 |
| `quadrant_user_data:default_backup_1` | 备份 2 | 同上 |
| `quadrant_user_data:default_backup_2` | 备份 3 | 同上 |
| `quadrant_user_data:default_backup_3` | 备份 4（最旧） | 同上 |
| `quadrant_ui_theme` | 亮色还是暗色 | 可以删，删了回到亮色 |

**名字里 `default` 是用户标识**。本期只有一个用户，所以固定是 `default`。这样写是为了将来真的做登录功能时，不用改结构，加个用户就是新增一组 key。

**主题不放进用户数据里。** 因为主题是「这台设备看着舒服」的设置，不该跟着数据同步到别的设备去。

**主数据对象里永远只有三样东西**：`user` / `schemaVersion` / `dates`（见 2.3）。这不是审美问题，是条安全规矩——**只要数据对象里没有别的东西，导出、备份就永远带不出去别的东西**。等下一版加同步凭据时，这条规矩就是防止密码泄露的那道门（见第六章）。

**已经废弃的 key**：早期设计里有一个 `quadrant_last_date`（记住上次看的是哪天）。现已取消——每次打开都默认停在**今天**（见 1.5）。这个 key 从未写进任何用户设备，不需要处理。

#### 安卓 App 里还有两份数据

都在 Capacitor Preferences 中：

| Preferences 的键 | 装什么 | 作用 |
|---|---|---|
| `quadrant_prefs_backup` | 主数据的完整拷贝 | 系统回收 localStorage 后，靠它把数据救回来 |
| `quadrant_prefs_marker` | 一个「存过数据」的标记 | 区分「从没存过」和「存过但现在没了」 |

**`quadrant_prefs_marker` 必须存在 Preferences 里，这一点是关键。** 如果把它存在 localStorage，安卓回收 localStorage 时标记和数据会一起消失，程序就会判定成「这是新用户，从没存过数据」——于是**既不恢复、也不提示**，用户的数据无声无息全丢，那份救援副本等于白存。放在 Preferences 里，它才能和数据同生共死。

**什么时候写**：和主数据一起，每次保存后攒 3 秒写一次。不做成每敲一个字写一次——Preferences 每次都是整份重写，写太勤没有意义。

**什么时候读**：打开 App 时如果 localStorage 读不出来，**且 `quadrant_prefs_marker` 存在**（说明以前确实存过），就从 `quadrant_prefs_backup` 恢复，并明确告诉用户「已从本地副本恢复数据」。新用户第一次打开时标记不存在，正常显示空状态，**不弹恢复提示**。

### 2.3 数据长什么样

主数据就是一个 JSON，结构很简单：

```json
{
  "user": "default",
  "schemaVersion": 1,
  "dates": {
    "2026-10-01": {
      "I":   [ { "id": "id_1759_a1b2", "text": "写季度报告", "completed": false, "createdAt": 1759300000000 } ],
      "II":  [],
      "III": [],
      "IV":  []
    },
    "2026-10-02": { "I": [], "II": [], "III": [], "IV": [] }
  }
}
```

拆开看：

- `schemaVersion` 是**数据格式的版本号**，固定从 `1` 开始。现在看起来用不上，但它是给未来上的保险：将来一旦要加字段、改结构，代码就能靠它认出「这是老格式的数据」并做相应处理。**现在加是零成本，等有了真实用户再加，就得动所有人的数据。**
- `dates` 下面，**每个日期一个条目**，日期之间互相独立。改 10 月 1 号的内容，绝对不会影响 10 月 2 号。
- 每个日期下面固定有 `I` `II` `III` `IV` 四个列表，对应四个象限。
- **列表里的先后顺序，就是页面上从上到下的顺序。** 拖拽调整顺序时，实际就是把这个列表重新排一遍，不需要额外记「谁排第几」。

一个任务的字段：

| 字段 | 含义 |
|---|---|
| `id` | 唯一编号。用来区分「这是同一个任务」还是「这是两个不同的任务」 |
| `text` | 任务内容。**去掉首尾空格后不能是空的**，空的拒绝创建 |
| `completed` | 勾没勾上。**有阶段时这是个派生字段**，由阶段算出来（见 2.9） |
| `createdAt` | 什么时候建的。出问题时方便排查 |
| `stages` | **可选**。任务下面的阶段列表，每个阶段有自己的 `id` / `text` / `completed` / `createdAt`（见 2.9） |

**`stages` 没有的时候，这个任务就是一个普通任务**——加阶段之前存下来的数据全都是这样，它们必须照常能读、能导。

**v1.1 起，象限列表里的条目有两种**：普通任务（上面的形状，不变），以及**任务块**——它多一个 `type: 'block'` 标记和一个 `tasks` 子列表，形状见 2.10。没有 `type` 字段的条目都是普通任务，**老数据、老备份零影响**（和 `stages` 一样是纯追加，`schemaVersion` 仍为 1）。

**v1.1 起，主数据多一个与 `dates` 平级的顶层字段 `pool`**（计划池，形状见 2.11）：一个不按日期分的任务数组。老数据没有这个字段——读入时补一个空数组即可，`schemaVersion` 仍为 1。

### 2.4 备份、归档与自动恢复

这一节讲三件事：本地怎么滚动备份、本地怎么控制体积（30 天归档）、数据读不出来时怎么办。

#### 备份：4 份滚动历史

**为什么要备份**：`localStorage` 里的数据只有一份。程序如果因为某个 bug 把数据写坏了，或者用户手滑，没备份就真的找不回来了。

**怎么做**：

- 每次保存数据时，**顺手把上一版往后挪一格**，一共留 4 个历史版本。最旧的那个被挤掉。
- 挪备份这件事**最多 30 秒做一次**。因为用户快速勾选时会连续保存，每次都挪一遍会产生一大堆没意义的备份，纯属浪费空间。
- 每份备份里，除了数据本身，还要记一个**「这份备份是什么时候存的」时间戳**。因为 4.2 的恢复提示要告诉用户「已从备份恢复到 X 月 X 日 X 点的版本」——不记时间就报不出这个时间，那句提示只能变成一句没有信息量的空话。

#### 归档：本地只保留最近 30 天

本地数据滑动保留最近 30 天，更早的部分归档成一个 JSON 文件，交给用户自己的磁盘保存。

```
每次保存后检查
   ↓
本地日期跨度超过 30 天？
   ↓ 是
把超出 30 天的那部分打包成 JSON → 触发下载
   ↓
下载成功了没有？
   ├─ 成功了 → 从本地移除这部分数据
   └─ 没成功 → 本地数据一个字节都不动，改为提示用户手动归档
```

**这里有一条绝对不能违反的规矩：只有确认下载成功，才能从本地删数据。**

**为什么不写成「悄悄自动下载，下完就删」**：浏览器对**没有用户操作触发**的下载是会拦截的——弹窗拦截、连续多个下载拦截都很常见。如果程序不看下载结果，下完就删本地，那么归档文件根本没落盘、本地那份又删了，**数据当场蒸发**。所以流程必须是「下载成功 → 才删」；一旦被浏览器拦下，就不删，改成在界面上给一个「归档并下载」按钮让用户手动点（有用户手势，浏览器不会拦）。

**归档文件长什么样**：就是一个普通的导出 JSON，格式和 2.7 的 `.json` **完全一样**。所以将来直接当普通文件导入回来就能看，不需要任何特殊处理。

**导入归档文件之后**：如果导进来的数据跨度超过 30 天，程序会立刻再触发一次归档（同一条规则，不分数据来源）。这个行为要明确提示用户，否则用户会以为「刚导进来的东西又不见了」。

**界面和提示里必须说清楚**：本地只留 30 天，想回看更早的数据，需要把归档文件重新导回来。这句话不出现，用户就会以为数据丢了。

#### 数据读不出来时怎么办

```
读主数据 → 读失败
   ↓
挨个试 备份1 → 备份2 → 备份3 → 备份4
   ↓
试到哪个能读通，就用它把主数据恢复回去，并告诉用户恢复到了什么时候的版本
   ↓
四个备份全读不通
   ↓
进入「保护模式」（见下）
```

#### 保护模式：什么都读不出来的时候

四个备份全废，说明磁盘上那份原始数据多半已经损坏。这时候**最危险的动作是顺手用空数据把它覆盖掉**——一旦覆盖，那份「读不出来、但可能还能救」的数据就永远没了。

所以程序进入**保护模式**：

| 保护模式下 | 行为 |
|---|---|
| 页面显示 | 照常显示空四象限，顶部挂一条醒目的提示条 |
| 写操作 | **全部禁止**——添加、编辑、删除、勾选、拖拽一律不可用 |
| 磁盘上的原始数据 | **一个字节都不动** |
| 用户能做什么 | 点提示条上的「导入备份文件」；或者点「用空数据重新开始」 |

**为什么必须禁止写操作**：`store.js` 的保存是**整份重写**（见 1.7 规矩一）。只要允许用户编辑一次，保存就会把「空数据 + 新任务」写回主数据那个 key，**把那份可能还能救的原始数据永久覆盖**。所以「不覆盖原文件」这句承诺，只能靠「禁止写入」来兑现——光写在文档里是没有用的。

**「导入备份文件」做什么**：让用户选一份之前导出过的 JSON 导进来，写进主数据，然后解除保护模式。这是本版**唯一**的救援通道——因为数据本来就只在本地，用户手上那些导出的 JSON 就是最后一道保险。

> 本版没有云，所以这个按钮不叫「从云端恢复」。等第六章的同步做出来之后，这里会多一个按钮，但不是现在。

**「用空数据重新开始」要二次确认**，并明确警告「这会覆盖磁盘上现有的数据，且无法撤销」。

**关键：不管成功还是失败，都要让用户看见。** 最糟糕的做法是读失败后悄悄返回一个空的，用户以为自己的数据被清空了，其实还在磁盘上——只是程序没告诉他。这种情况一定要弹提示。

**这套备份挡不住什么**：4 份备份和主数据在同一个 localStorage 里，所以它只防「程序把数据写坏了」，防不住「系统把整个 localStorage 清空」——那种情况下 5 份一起消失。挡后一种情况要靠 2.1 说的安卓原生存储副本，以及用户自己导出的 JSON 文件。

### 2.5 导入与去重

导入就是选一个之前导出的 JSON 文件，把里面的数据并进来。

**检查格式，不合格就整个拒绝**：

```
读文件 → 内容不是合法的 JSON        → 拒绝，原数据一点不动，提示「文件格式有误」
       → 不是数据对象               → 拒绝，提示具体哪里不对
       → 缺少象限列表               → 拒绝，提示具体哪里不对
       → 日期格式不对               → 拒绝，提示具体哪里不对
       → 全部检查通过               → 才开始合并
```

**先全部检查完，确认没问题，再写数据。** 不能边读边写——中途发现有问题时，已经写进去的那部分就留在里面了，数据会变得半新半旧。

**导入是「合并」，不是「覆盖」**：文件里的数据并进本地，**本地已有的东西一条都不会被删掉**。本期不做「用文件替换本地全部数据」那种模式——那种模式风险太高，用户拿一份不完整的旧备份导入，就能把本地较新的数据全部清掉。

**怎么算重复**：如果两个任务的**象限**和**文本内容**都一样，就认为是同一个任务，跳过不插入。判断用「内容」而不是用「编号」——因为同一个任务在两台设备上各自创建时，会拿到两个不同的编号，靠编号判断的话会重复插入一堆一样的任务。

**判重的比较范围就是「那一天」。** 合并时按日期分桶进行，**只看当前这一天已有的数据，别的日期不参与比较**（见 D-09）。

| 情况 | 结果 |
|---|---|
| 同一天里，象限和文本都相同 | 算同一条，跳过不插入 |
| 同一天里，象限不同、文本相同 | 两条都保留（比如同一天 I 和 III 各有一条「开会」） |
| 不同日期的任务 | **不比较**，各日期本来就相互独立（见 2.3） |

> **写代码时这一条最容易出错**：判重函数的入参必须是「**某一天的那一份数据**」，而不是「整个 `dates` 对象」。一旦漏传日期、拿全量去比，10 月 1 号和 10 月 2 号的同名任务就会被当成同一条——「写日报」这种每天都要做的任务会被吃掉 29 天，而用户只看到一句「跳过 N 条」，事后根本查不出少了什么。`test-import-merge.js` 里必须专门覆盖这一条。

**导入后要告诉用户结果**：比如「新增 12 条，跳过 3 条」。不然用户不知道导入到底成没成功。

**已确定：不看勾选状态**（见 D-16）。文本相同就算同一个任务；跳过后**保留本地已有的勾选状态**，不被文件里的状态覆盖。

**阶段也不参与判重。** 判重键还是只有「象限 + 文本」两项——阶段不一样不算两条任务。跳过的那些，**本地的阶段原封不动**，不会被文件里的盖掉。新增的那些，阶段跟着一起搬过来，但**阶段编号全部换成新的**（和任务编号一个道理：文件里的编号在本地可能撞车）。

**导入归档文件之后**：如果导进来的数据跨度超过 30 天，会立刻触发一次归档（见 2.4）。这个行为要提示用户，否则用户会以为刚导进来的东西又不见了。

### 2.6 导出格式

| 格式 | 内容 | 网页版 | 安卓 App | 用途 |
|---|---|---|---|---|
| `.json` | 本地全部数据 | ✅ | ✅ | **唯一能重新导入回去的格式**，最重要的备份；30 天归档也是它（见 2.4） |
| `.md` | 按日期排好的四象限文本 | ✅ | ✅ | 存档、也用来生成 PDF |
| `.pdf` | 由 `.md` 打印而来（见 4.4） | ✅ | ❌ | 阅读、打印、发给别人 |
| `.zip` | JSON + Markdown 打包成一个文件 | ✅ | ✅ | 手机上一键保存两种文本格式 |

**导出里绝对不含主题设置**，因为主题是本机偏好，不是数据（D-11）。

**导出文件就是跨设备的唯一通道**（本版没有云）。它会被用户发到微信、传到网盘、拷到 U 盘——所以要假设**它会离开这台设备**。任何不该外流的东西都不能进这个文件，这是 2.2 那条"主数据对象里永远只有三样东西"的规矩要守住的真正原因。

**阶段在 `.json` 里是原样的结构；在 `.md` 和 PDF 里缩进一层。** 任务和阶段是两级列表，一眼看得出从属关系：

```
- [ ] 写季度报告
  - [x] 收集数据
  - [ ] 写初稿
```

**PDF 只有网页版有。** 安卓端不提供 PDF 导出，原因见 4.4——那不是在安卓上多写几行代码就能补上的，而是这条路在安卓上根本走不通。

**`.md` 和 `.zip` 里装的是本地全部日期的数据**，不是只有当前这一天——它们是给存档用的，只存一天没什么意义。验收时「内容和页面上的数据一致」，指的是**当前这一天那一段**对得上。

**zip 里固定就是 JSON + Markdown 两件**，不做按需勾选（见 D-18）。**为什么 zip 里没有 PDF**：PDF 是由浏览器或系统打印生成的，程序**拿不到 PDF 的字节**，也就没法把它塞进压缩包。这不是实现偷懒，是这条路的物理限制，详见 4.4。

**zip 是自己手写的**（见 D-05），所以它被单独验过：`test-zip.js` 会把打包出来的字节**重新解析一遍**（签名、大小、CRC、偏移逐项核对），另外还用 Windows 自带的 `Expand-Archive` 真解压过一次，解出来的内容与原文**逐字节一致**。手写 ZIP 最容易出的错是 CRC 或偏移算错——那种情况下压缩包在文件管理器里看着正常、也能列出文件，**只有解压时才报「文件损坏」**，而那时用户已经以为备份好了。

### 2.9 阶段：把任务拆成几步

**是什么**：一条任务下面可以挂一层「阶段」。比如「写季度报告」= 收集数据 → 写初稿 → 审阅 → 定稿。每个阶段有自己的文字、自己的勾选状态。

**为什么要有它**：一件事只要超过两三步，用户就得二选一——要么把每一步都写成独立任务（列表瞬间被淹没），要么只写一条大任务（做完了多少完全看不出来）。阶段就是给这个中间地带准备的。

#### 四条定死的规矩

| # | 规矩 | 为什么 |
|---|---|---|
| 1 | 阶段**只有一层**，阶段下面不能再挂阶段 | 多一层，界面和数据都要复杂一大截，而收益很小 |
| 2 | **父任务的完成状态只由阶段决定** | 有阶段的任务自己不能「完成」——完成的定义就是「所有阶段都勾完了」 |
| 3 | 阶段**只能在同一个任务内部**换顺序 | 不能从 A 任务拖到 B 任务 |
| 4 | **没有阶段的任务，它自己就是一个条目** | 勾选框就是它自己 |

#### 任务行的勾选框 = 「把这一条整个勾上 / 取消」

这是规矩 2 和 4 合起来的结果，也是**最容易写错的地方**：

| 这条任务 | 勾选框的含义 | 它显示的勾选状态 |
|---|---|---|
| 没有阶段 | 任务自己的完成状态 | 任务自己的 `completed` |
| 有阶段 | **一键把所有阶段一起勾上 / 一起取消** | 所有阶段是不是都勾完了 |

所以「父任务能不能自己完成」这个问题的答案是：**不能**。那个勾选框只是个一次性勾完全部阶段的快捷方式。

实现上只有一处判断（`task-ops.toggleTask`）：有阶段就遍历阶段，没阶段就改任务自己。别在界面层再判断一次——两处判断迟早会不一致。

#### 统计按「最细的可勾选单位」算

有阶段就数阶段，没阶段就数任务自己：

| 今天有这些 | 算成 |
|---|---|
| 写季度报告（5 个阶段，勾了 3 个） | 5 条，完成 3 |
| 回邮件（没有阶段，没勾） | 1 条，完成 0 |
| 准备分享（2 个阶段，都勾了） | 2 条，完成 2 |
| 买咖啡豆（没有阶段，没勾） | 1 条，完成 0 |
| **合计** | **总数 9，已完成 5，完成率 56%** |

这条口径**同时管两处**：顶部的「已完成 / 总数 / 完成率」，以及每个象限标题栏上那个数字。

**两边必须用同一个算法**（`task-ops.getProgress`），否则会出现「象限里写着 2、顶部总数却是 7」这种对不上的数。为此 render.js 的 `progressOf` 是由 app.js 传进去的，不是它自己算的。

#### 数据长什么样

```json
{
  "id": "id_1759_a1b2",
  "text": "写季度报告",
  "completed": false,
  "createdAt": 1759300000000,
  "stages": [
    { "id": "id_1759_c3d4", "text": "收集数据", "completed": true,  "createdAt": 1759300001000 },
    { "id": "id_1759_e5f6", "text": "写初稿",   "completed": false, "createdAt": 1759300002000 }
  ]
}
```

**`stages` 是可选的。** 这一点很关键：加阶段之前导出的备份里全都没有这个字段，它们必须能照常读进来、导进来（见 3.4 那条往返要求）。要是把它写成必填，用户手里那些备份就全废了。

**`completed` 是个派生字段。** 有阶段时它一律由阶段算出来并写回；数据里如果和阶段对不上（手工改过、别的版本写的），**一律信阶段**——阶段是用户一条条点出来的，更可信。

**`schemaVersion` 保持 1，没有升到 2。** 因为这次是纯追加：老数据完全合法、不需要任何转换，新代码读老数据也不会丢东西（专门的往返测试盯着这件事）。版本号只在「老数据需要转换」时才值得动，每次加字段都升一下只会让它变成噪音。

#### 界面：默认折叠

有阶段的任务点任务行右边的三角展开。**为什么默认折叠**：四象限本身就是 2×2 网格，地方很紧——每个任务都铺开五个阶段，一屏就装不下几条任务了。折叠时占的地方和没有阶段时**完全一样**。

```
折叠时：
┌─ I 重要且紧急 ────────── 3/6  ＋ ┐
│ ☐ 写季度报告      3/5  ▸ ＋ ×     │
│ ☐ 回邮件               ＋ ×      │
└──────────────────────────────────┘

展开后：
┌─ I 重要且紧急 ────────── 3/6  ＋ ┐
│ ☐ 写季度报告      3/5  ▾ ＋ ×     │
│     ☑ 收集数据             ×     │
│     ☑ 写初稿               ×     │
│     ☐ 审阅                 ×     │
│ ☐ 回邮件               ＋ ×      │
└──────────────────────────────────┘
```

**展开状态存在内存里，不进用户数据。** 它不属于「用户的任务」，没必要跟着导出和备份跑。刷新页面就全折叠——这正是「默认折叠」想要的效果。

#### 排序：只靠拖拽

阶段排序**只靠拖拽**，不放上移/下移的小箭头——那两个箭头占地方、在手机上还不好点，拖拽一条路就够了。

拖拽复用了任务那套 Pointer Events 机制，只在三处不同：

| | 落点找谁 | 能不能跨出去 |
|---|---|---|
| 拖任务 | 指针底下那个象限 | 能，四个象限随便拖 |
| 拖阶段 | 按下的那一刻就定死的那条任务 | 不能，只能在任务内部挪 |

> **实现上有个坑**：阶段的 `<li>` 套在任务的 `<li>` 里面。按下的瞬间要是先判断「这是不是一个 task」，拖阶段就会变成拖整条任务——而且拖起来还挺像回事，非常难发现。所以 `drag.js` 里**必须先判断 stage，再判断 task**。

#### 一个容易被当成 bug 的行为

**把阶段全删光之后，父任务的状态停在最后一次同步的值上。**

比如三个阶段全勾完（任务 = 已完成），然后把三个阶段删掉——任务保持「已完成」，**不会**变回未完成。

这是有意的：用户把它标完成了，删掉步骤不该把它变回未完成。写在这里，免得以后被当成 bug「修」掉。

### 2.10 任务块：装着一批任务的大条目（v1.1）

**是什么**：象限列表里的一种「容器条目」。块有自己的名字，里面装若干条**任务**。比如「装修」这个块，里面装「量房」「买材料」「找工人」三条任务。

**为什么要有它**：一批一起做的事（同一个项目、同一个主题），散在象限里就是一串平铺的行，看不出谁和谁是一伙的。块给这批任务一个看得见的边界，还能整批拖走。

#### 四条定死的规矩（和阶段那四条一个写法）

| # | 规矩 | 为什么 |
|---|---|---|
| 1 | 块**只有一层**：块里只能装任务，不能装块 | 和阶段同一个道理——多一层，界面和数据都复杂一大截，收益很小 |
| 2 | 块的完成状态**只由块内任务决定**；块的勾选框 = 一键把块内任务全勾上 / 全取消 | 和阶段规矩 2 一致。空块没有可勾的东西，勾选框点了无效果 |
| 3 | 块和任务在象限列表里**混排**，先后就是列表顺序 | 沿用 D-10：顺序由列表先后决定，拖拽直接重排列表，不额外记「排第几」 |
| 4 | **空块合法** | 刚建出来的块就是空的，先建块再往里拖任务是正常用法 |

#### 数据长什么样

```json
{
  "id": "id_1759_b1c2",
  "type": "block",
  "text": "装修",
  "completed": false,
  "createdAt": 1759300010000,
  "tasks": [
    { "id": "id_1759_d3e4", "text": "量房", "completed": false, "createdAt": 1759300011000 },
    { "id": "id_1759_f5a6", "text": "找工人", "completed": false, "createdAt": 1759300012000,
      "stages": [ { "id": "id_1759_g7h8", "text": "比价", "completed": false, "createdAt": 1759300013000 } ] }
  ]
}
```

- `type: 'block'` 是**唯一的标记**。没有 `type` 的条目都是普通任务——老数据零影响，`schemaVersion` 不动（纯追加，见 2.9 同一条理由）。
- 块内条目的形状和象限里的任务**完全一样**（可以有 `stages`），所以勾选、编辑、阶段、统计全部复用任务那套逻辑，不另写一份。
- 块内条目**不允许再是块**。`store.js` 整理数据时遇到嵌套块直接丢弃（脏数据），导入检查遇到嵌套块整份拒绝（来路不明的数据不救，见 2.5 的分工）。
- `completed` 是派生字段：块内所有「最细可勾选单位」都完成才算完成。空块一律未完成（`allDone([])` 若照搬阶段的写法会算成 true，这里必须特判）。

#### 定位与操作（task-ops.js）

一条任务现在可能躺在两个地方：象限顶层，或某个块的 `tasks` 里。所以**定位函数必须能穿透块**：

```
findItem(data, dateStr, quadrantId, itemId)
  → 先查顶层列表（任务和块都在这），再查每个块的 tasks
  → 返回 { kind: 'task'|'block', blockId: null|块id, index, item }
```

app.js 从 DOM 上只拿得到一个 id，**它不需要知道自己点的东西在不在块里**——编辑、勾选、删除、加阶段全都先走 `findItem`，在哪儿就地在哪儿改。这是这次改动里最重要的一条：如果让上层先判断「在不在块里」再挑函数，迟早有一处忘判断。

操作一览：

| 操作 | 行为 |
|---|---|
| `addBlock` | 在象限顶层末尾建一个空块 |
| `editItem` | 改块名或任务文本（同一个函数，按 `kind` 分派） |
| `toggleItem` | 块 → 一键全勾/全取消块内任务；任务 → 原逻辑 |
| `removeItem` | 块 → 连块内任务一起删；任务 → 从顶层或块内删 |
| `moveItem` | 见下 |

`moveItem` 的落点有两种：

```
{ quadrantId, index }               → 象限顶层第 index 位（块只能落这种）
{ quadrantId, blockId, index }      → 某个块内 tasks 的第 index 位（只有任务能落这种）
```

规矩 1（块不能进块）在数据这一层强制：`moveItem` 收到「块 + 块内落点」时按顶层落点处理。

#### 统计口径

块自身**不计数**，数的是它内部的最细可勾选单位：

| 今天有这些 | 算成 |
|---|---|
| 块「装修」（内含 2 条任务，其中 1 条带 2 个阶段） | 4 条（1 + 1 + 2） |
| 普通任务「回邮件」 | 1 条 |
| **合计** | **总数 5** |

`getStats` 和象限标题栏的计数必须走**同一个函数**（`progressOfItem`：块就聚合、任务就 `getProgress`）——这是 2.9「两边一个算法」规矩的直接延伸。

#### 界面

- 象限标题栏右上角两个符号：「＋」加任务（原有），「▣」加任务块（新）。D-30 的延伸：同样 32×32 点击区、`aria-label`、不随视觉缩小。
- 块头：勾选框 + 块名 + 进度 `n/n` + 三角 + ×；块体：块内任务列表（形状和顶层任务一样）。空块显示「把任务拖进来」占位。
- **块默认展开**——和阶段（默认折叠）相反。阶段是任务自己的细节，折叠省地方；块是容器，折叠了用户就没法看见里面有什么、更没法往里拖。展开状态存内存不进数据（沿用 D-33 的口径），但状态表是独立的一份（`collapsedBlocks`），语义是「默认开、记关」。
- 点块名改名：和任务编辑同一套交互（D-31：原地变输入框，回车/失焦提交、Esc 取消、改空拒绝并恢复）。改名期间块体暂时收成一个输入框，提交后恢复。

#### 拖拽

可拖对象从两种变三种。**判定顺序：阶段 → 块 → 任务**——2.9 那个坑升级了：块的 `<li>` 里套着任务的 `<li>`，先判任务的话，拖块头会变成拖块里第一条任务，或者把块内任务误当成顶层任务。

| 拖什么 | 落点怎么算 | 能不能跨象限 |
|---|---|---|
| 阶段 | 按下时定死的那个任务内部（不变） | 不能 |
| 块 | 指针底下象限的**顶层**位置（规矩 1 的界面侧） | 能，块内任务跟着走 |
| 任务 | 指针在**块头上** → 进那个块的末尾；在**块内任务上** → 那个块内的对应位置；**其余** → 指针底下象限的顶层位置 | 能（进出块、跨象限都是这一个手势） |

两个实现要点：

- **顶层落点只数顶层的 `<li>`**（遍历容器的直接子元素），不能用 `querySelectorAll('.task')`——那会把块内的任务也数进去，index 就乱了。
- 往块里拖时占位符插进块的 `<ul>` 里，用户能看出「会落到块内」，其余沿用任务那套占位符。

#### 导出与导入

- Markdown / PDF：块多缩进一层（块 → 块内任务 → 阶段，三级列表），块名加粗。
- JSON：原样带出（导出永远是整份数据序列化，天然带块）。
- 导入检查认识块：`type === 'block'` 时 `tasks` 必须是列表、每条子项必须合法；**嵌套块整份拒绝**。
- 合并：块级判重仍按「象限 + 文本」（D-09），块内条目**不单独判重**、随块整体搬，编号全部换新（文件里的编号在本地可能撞车，和任务编号同一个道理）。

### 2.11 计划池：现在不做、以后再安排的事（v1.1）

**是什么**：四象限下方的一块独立面板。象限里的任务点「推迟」就进池；池里的任务可以拖回任意象限、可以删除、可以改文字、可以设定一个**完成时间**（二期）。

**为什么要有它**：「这件事该做但现在排不进今天」是四象限的真实高频状态。没有池，用户只能把它留在某个象限里占地方，或者删掉——两条路都丢信息。推迟 = 从「今天的安排」里拿出来，但**不销毁**。

#### 数据长什么样

```json
{
  "user": "default",
  "schemaVersion": 1,
  "dates": { "……": "……" },
  "pool": [
    { "id": "id_1759_p1a2", "text": "整理相册", "completed": false,
      "createdAt": 1759300020000, "plannedDate": "2026-10-02" }
  ]
}
```

- `pool` 是**与 `dates` 平级的顶层字段**，一个数组。**不按日期分**（为什么，见 D-37）。
- 池内元素的形状**就是任务**（可以有 `stages`）——进池出池都是同一个对象搬位置，字段零转换。
- `plannedDate`（二期）：任务身上的**可选**字段，'YYYY-MM-DD'，表示「打算哪天完成」。**没有这个字段 = 未设定**（和 `stages` 同一个思路，缺省即「空」），任务**持续保留**在池中。`normalize` / 导入检查对它只做格式校验：合法就保留，不合法就丢掉这个字段（任务本身照留）。象限里的任务也可以带这个字段（数据层一视同仁），只是界面上只有池内提供设定入口。
- 老数据没有 `pool`：读入时补空数组，`schemaVersion` 不动（纯追加）。
- `normalize` 清洗：`pool` 不是数组就丢掉重来（空数组）；元素按任务的清洗规则走，文本为空的丢弃。

#### 操作（task-ops.js）

| 操作 | 行为 |
|---|---|
| `postponeTask` | 把一条任务从象限（顶层；数据层不禁止块内，但界面只给顶层入口，见下）摘出来，压进 `pool` **末尾**。文字、完成状态、阶段原样带走。二期起顺带写 `plannedDate = 被推迟任务所属日期 + 1 天`（requirements 第 3 条：默认下一天、可修改） |
| `addPoolItem`（三期） | 池内**直接添加**一条任务，压进 `pool` **末尾**。`plannedDate = 当前查看日期 + 7 天`（用户指令：手动添加的默认 7 天后）。与推迟进来的任务完全同构——之后的拖回 / 删除 / 改文字 / 导出导入零差别 |
| `postponeStage`（二期） | 把一条**阶段**从父任务里摘出来，保存为池内的一条**任务**：文本为 `[所属任务文本]阶段文本`（requirements 第 3 条第 2 款），完成状态照抄阶段自己（没有子阶段，不建 `stages` 字段），`plannedDate` 同样默认下一天。父任务删掉这条阶段后走「删光阶段状态停住」的规矩（见 2.9）；宿主块跟着重算（规矩 2） |
| `restoreFromPool` | 把池里一条任务放回**指定象限**：拖拽回来时按占位符指示的位置插（`toIndex`，越界夹紧）；不带 `toIndex` 时排**末尾**（沿用 addTask 的位置逻辑，不挤乱用户排好的顺序） |
| `removePoolItem` | 从池里删除一条 |
| `editPoolItem` | 改池内任务文字；改空拒绝（同 D-31） |
| `setPoolDate`（二期） | 设定 / 修改 / 清除池内任务的 `plannedDate`：传 'YYYY-MM-DD' 设定，传 `null` 清除（回到「未设定」）。日期格式不合法拒绝、原值保留 |

#### 为什么推迟的默认是「所属日期 + 1」

用户在**查看 X 日**的时候推迟 X 日的任务，「下一天」自然的基准是 X + 1——任务本来就属于 X 日。不用「真实今天 + 1」的原因：查看过去的日期时（比如补记前天的安排），推迟出来的会是已经过去的时间，用户还得手动改一遍；基准跟着被推迟任务所属的日期走，得到的默认值永远在未来方向。

#### 为什么手动添加的默认是「查看日期 + 7」（三期）

用户指令：池里手动添加的任务默认 7 天后。推迟是「这件事明天再说」（+1），手动添加是「近一周要做的事」——给一个明确但宽松的默认，比「未设定」更符合手动添加的语义（用户既然肯动手写，通常心里有个大致期限；7 天让他不用立刻面对空白）。基准用**当前查看的日期**而不是真实今天，和上面推迟默认同一个道理：查看过去日期时添加，不会得到一个已经过去的时间。默认值永远可改可清，不会把用户锁住。

#### 推迟阶段的几条细则（二期）

- **阶段变任务，单向、不逆转**：进池的就是一条普通池内任务，不再记住「我曾经是哪个任务的哪个阶段」。要回去只能拖回象限或手动改文字——不做「还原成阶段」，那一期用不上。
- **中括号前缀是内容，不是元数据**：`[父文本]阶段文本` 直接拼进 text 字段。不用单独字段记父任务 id，是因为父任务可能先被删掉、改文字、甚至也进了池——挂引用就得处理一堆悬空的情况，拼进文本则永远自解释（requirements 的原话就是「在文本内容前用中括号标注」）。
- **父文本也走一遍 trim / 转义链**：文本里的 `[` `]` 不做处理——前缀只是给人看的标注，不做解析还原。
- 只允许推迟「任务」或「阶段」（requirements 第 3 条第 1 款）：块整体永远没有推迟入口。

#### 统计与归档

- `getStats` 只扫 `dates`，`pool` **天然不计入**——不需要写任何排除代码，口径自动正确。
- 30 天归档只收缩 `dates`（按日期），`pool` 没有日期，**归档不动它**。池会慢慢变大，这是接受的：池是用户手动管理的待办停车场，一期不做自动清理。

#### 界面

- `index.html` 在 `#quadrants` 后面加一个 `<section id="pool">`，横向铺满一行。
- 池头部：名称 + 计数 + 「＋」按钮（三期）。点「＋」在池列表**末尾**长出一个输入框（复用 `task__input`，D-31 同一套交互：回车 / 失焦提交、Esc 取消、空文本安静取消），提交走 `addPoolItem`。**进池入口因此是两个：象限「推迟」+ 池内「＋」**——两个都是明确的点击，和 D-37「拖拽不许进池」不冲突（防的本来就是「拖到空白处」的失手）。
- 池内每一行：任务文本 + 删除「×」。**没有勾选框**——池里是「待安排」，不是「正在做」，显示勾选框会诱导用户在池里勾任务（池内任务的完成状态只是进池前的历史遗留，进池后不再推进）。
- 空池显示一句占位：「计划池是空的。点任务行上的『推迟』，把暂时不做的事放进来。」
- 「推迟」按钮：**只有顶层任务**的行上有（文字按钮「推迟」，悬停显形、移动端常显，与删除按钮同款）。块内任务没有——块是手动分组的整体，不随单个任务的推迟而拆散；要推迟先把它拖出块。块本身也没有推迟按钮。
- 「阶段」行的推迟按钮（二期）：展开阶段列表后，每个阶段行上有同款「推迟」——阶段是这一期新加的推迟对象（requirements 第 3 条）。点它走 `postponeStage`。
- 池内行的时间显示与设定（二期）：文字后面跟一个时间片段——未设定显示「未设定」（暗色小字），已设定显示日期（'YYYY-MM-DD'）。点它**原地**换成一个 `<input type="date">`（和任务编辑同一套 D-31 交互：回车 / 失焦提交，Esc 取消），旁边一个「清除」把时间清回未设定。没设时间的任务**持续保留**在池里，不参与任何提醒或清理（本期根本没有提醒）。
- 点池内文字改文字：和任务编辑同一套交互（D-31）。
- 保护模式：推迟 / 拖回 / 删除 / 改文字全部禁止（按钮 `is-readonly` 样式 + 调用前拦截，与其它写操作同款）。

#### 拖拽

- **池 → 象限**：池内任务可以拖进四个象限的任意位置（顶层落点，同任务拖拽那套占位符）。落点解析复用现有逻辑，`onDrop` 时走 `restoreFromPool`。
- **象限 → 池：不允许**。进池只有「推迟」按钮这一个入口——拖拽进池会和「拖到象限下方空白处」的失手混淆，而且推迟是明确意图，值得一次明确的点击。
- 池内排序：一期不做。池的顺序就是进池先后（新的在最后），靠 `createdAt` 也能看出来。

#### 导出与导入

- JSON 导出原样带 `pool`（整份序列化，天然带上，`plannedDate` 跟着走）。
- 导入检查：`pool` **可选**（老文件没有是合法的）；有则必须是数组、元素按任务规则检查，坏的整份拒绝。`plannedDate` **可选**：没有是合法的（老备份）；有则必须是 'YYYY-MM-DD' 合法日期，**格式不对丢字段不拒整份**——时间是附加信息，不该让它拦住任务本身（和 store.js「尽量救」同一个取舍）。
- 合并：池内判重只按**文本**（池没有象限和日期可比），相同文本跳过；编号全部换新，`plannedDate` 照抄文件里的值。

### 2.12 完成时段：早上到晚上的六选一标记（v1.1）

**是什么**：任务或阶段身上的一个**时段标记**——这件事打算在一天的哪一段完成。六个时段：早上 / 上午 / 中午 / 下午 / 傍晚 / 晚上（requirements 第 4 条的「6 个图标」）。它本身不改变任何行为，唯一的消费方是 2.13 的时间视图——按它分组。

#### 数据长什么样

```json
{
  "id": "id_1759_p1a2", "text": "取快递", "completed": false,
  "createdAt": 1759300020000, "slot": "下午"
}
```

- `slot` 是任务和阶段身上的**可选字段**，值就是六个中文串之一。**缺字段 = 未设定**（和 `stages` / `plannedDate` 同一个思路）。
- **值直接存中文，不存代号**：导出的 JSON 是给人看的（2.6），`"slot": "下午"` 比 `"slot": "afternoon"` 可读；六个值本身是白名单（`CONFIG.SLOTS`），不存在需要映射的别名。选项上的 emoji 图标（🌅 早上……）**只存在于渲染层**，不进数据。
- 老数据没有 `slot`：什么都不用做（缺省即未设定），`schemaVersion` 不动（纯追加）。
- `normalize` / 导入检查：值存在但不在六值之内 → **丢字段保任务**，与 `plannedDate` 同一条取舍（标记是附加信息，不该拦住任务本身）。

#### 谁可以有时段

| 对象 | 有没有时段 | 为什么 |
|---|---|---|
| 没有阶段的任务 | 有，任务行上 | 它自己就是一个可完成条目 |
| 有阶段任务的**各阶段** | 有，每个阶段行上各一个、互不影响 | 阶段是此时最细的可完成单位 |
| 有阶段任务的**本体** | **没有** | 它的完成安排由各阶段决定——和统计「数最细单位」同一个口径；否则同一件事出现两个时段，时间视图不知道听谁的 |
| 任务块本体 | 没有 | 块是分组容器，不是可完成单元（2.10）；块内任务照常有 |
| 计划池任务 | 数据层字段保留，界面**不提供**入口 | 池是「待安排」，连日期都未定，谈不上时段；拖回象限后照常设定 |

#### 操作（task-ops.js）

| 操作 | 行为 |
|---|---|
| `setSlot` | 设定 / 清除一条任务的 `slot`：传六值之一设定，传 `null` 清除（删字段，回「未设定」）。值不在白名单 → `ERR.BAD_SLOT`，原值保留 |
| `setStageSlot` | 同上，作用于某条阶段（`locateTask` + `findStage` 定位，块内任务一样能用） |

时段是**纯标记**：两个操作都不碰 `completed`、不碰统计、不触发重排序——改完只是数据里一个字段的值变了。

#### 界面

- 行上的控件是**原生 `<select class="slot__select">`**（为什么不用自绘弹层 / 图标网格，见 D-39）：第一项 `value=""` 显示「未设定」，其余六项是 `🌅 早上` 这样的「emoji + 文字」，选中哪项显示哪项。
- `<select>` 进 drag.js 的 `isInteractive` 排除名单——按它不能触发拖拽；`change` 事件在 app.js 统一收口（和勾选框同一个监听器），按目标是任务行还是阶段行分流到 `setSlot` / `setStageSlot`。
- 保护模式：`is-readonly` 样式禁点 + `change` 处理器里照常拦截，与其它写操作同款。

#### 与时间视图的关系

2.13 的时间视图按 `slot` 给**当天**的任务分组；没设时段的任务不进任何组。时段不是唯一键——同一个时段下有几条都行。

### 2.13 时间视图：按时段重排的一天（v1.1）

**是什么**：把「当前这一天」的任务从「按象限分」换成「按完成时段分」再看一遍（requirements 第 5 条）。四象限回答「这件事多重要多急」，时间视图回答「这一天从早到晚怎么过」——同一份数据的第二种看法。

**不新增任何数据**：分组完全靠 2.12 的 `slot` 字段现算，视图本身是纯展示。

#### 分组怎么算（task-ops.js）

`getTimeView(data, dateStr)` 返回 `[{ slot, items }]`：

- **只出现有任务的时段**（requirements：「根据时间段数量展示对应内容」），顺序固定为 `CONFIG.SLOTS` 的从早到晚。
- 扫当天四个象限的顶层任务和**块内任务**（块被拍平——块是分组不是内容，视图里没有块的位置；块内任务带 slot 就进组）。
- 没阶段的任务：`slot` 在任务身上，进组的是任务本体。
- 有阶段的任务：**进组的是设了 slot 的那些阶段**，条目带 `parentText`（所属任务文本）做标注；任务本体不进（它没有 slot 入口，见 2.12）。
- 每个条目带 `quadrantId` / `taskId` / `stageId`——视图本期只读，但这些 id 留着，以后要在时间视图里操作不用再改数据结构。
- 没设时段的任务 / 阶段不进任何组；计划池不进（池不按日期分，D-37）。

#### 界面

- 顶栏日期区右侧加「时间视图 / 四象限」切换按钮；当前视图 = **界面状态存内存**（`state.view`），刷新回四象限（四象限是主视图，见 D-33 同类取舍）。
- 时间视图打开时：`#quadrants` 与 `#pool` 隐藏，`#timeview` 显示；切回原样恢复。日期切换照常工作——时间视图显示的是**当前查看日期**的分组。
- 布局：**网页版两列网格**（CSS Grid `repeat(2, 1fr)`，N 个组自动排成两列多行——4 组即 2×2，requirements 的原例）；**≤600px 单列**。这和四象限的 2×2 / 单列是同一套响应式断点（见 3.3）。
- 每组：时段图标 + 名称 + 条数，下面列出条目；完成的条目删除线 + 降透明度（与象限里同一个视觉语言）。阶段条目在文本后用暗色小字标注「· 所属任务文本」。
- **只读**：没有勾选框、没有编辑入口（D-40）。空态：当天一条设了时段的任务都没有时显示一句提示，而不是空白页。

### 2.14 模板：把某一天存成能反复用的底稿（v1.1）

**是什么**：把「当前查看日期」的四象限任务表整个存成一份**模板**，以后可以一键填充到别的日子（requirements 第 6 条）。适合「每周一例会日的固定安排」这类反复出现的结构。

#### 数据长什么样

```json
{
  "templates": [
    { "id": "id_1759_t1", "name": "2026-10-01", "createdAt": 1759300020000,
      "items": { "I": [ …任务或块… ], "II": [], "III": [], "IV": [] } }
  ]
}
```

- `templates` 是**与 `dates` 平级的顶层字段**（和 `pool` 同款），不按日期分。老数据没有 → 读入补空数组，`schemaVersion` 不动（纯追加）。
- `items` 是那一天四个象限的**深拷贝**：任务、阶段、任务块、勾选状态、`slot`、`plannedDate` 原样保留。模板是副本不是引用——之后改那天的任务，模板不动。
- `name` 缓存时自动定为**当天日期串**（如 `2026-10-01`），用户可改。

#### 「覆盖同名」怎么判定（requirements 的原话）

**不需要「是否重命名过」的标记位——规则是纯按名字走的**：

- 缓存 X 日的任务表 → 自动名就是 `X`。
- 列表里已有名叫 `X` 的模板 → **覆盖**它的 `items`（这就是「没重命名时，重新缓存会覆盖同名缓存项」：没改名，名字就还是 `X`）。
- 用户把那份模板改名成了「周一例程」→ 列表里不再有叫 `X` 的 → 重新缓存 X 日**新建**一条。

一句话：**覆盖不覆盖，看名字撞不撞**，和「用户有没有重命名」自然等价，不用存多余的状态。

#### 操作（task-ops.js）

| 操作 | 行为 |
|---|---|
| `saveDayAsTemplate` | 把 `dateStr` 那天的四象限深拷贝进模板：有同名（自动名 = 日期串）模板则覆盖其 `items`，否则新建。**空的一天拒绝**（`ERR.EMPTY_DAY`）——没有内容的模板没有意义 |
| `renameTemplate` | 改模板名；改空拒绝（同 D-31） |
| `removeTemplate` | 删除一份模板。不影响任何日期的任务（副本，不是引用） |
| `applyTemplate` | 把模板内容填充进**指定日期**：全部条目深拷贝、**编号全部换新**（同一台机器上可能应用多次）、**勾选状态清零**（模板是计划不是记录——阶段清零后父任务与块按规矩重算）。同一天同一象限已有**同文本**条目的跳过（防重复应用出双份，和导入判重同一个思路），返回 `{ added, skipped }` |

应用时 `slot` / `plannedDate` 照抄模板——时段本来就是「几点做」的安排，跟着模板走才对。

#### 界面

- `#templates` 面板挂在 `#timeview` 之后（四象限视图的一部分；切到时间视图时和池一起隐藏）。
- 头部：名称 + 计数 + 「存今天为模板」按钮 → 走 `saveDayAsTemplate`，覆盖时 toast 说清是覆盖。
- 每行：模板名 + 「应用」「改名」「删除」。应用 = 填充到**当前查看的日期**（不是固定回原来那天——模板的价值就在于搬到别的日子）；改名是原地输入框（D-31 同款交互）；删除不弹确认（模板随时能再缓存一份，代价低——但 toast 说清楚删的是哪份）。
- 保护模式：四个操作全禁（与其它写操作同款）。

#### 导出与导入

- JSON 导出原样带 `templates`。
- 导入检查：`templates` **可选**；有则必须是数组，每份模板严格检查（名字合法、`items` 四个象限键齐全、条目走任务/块的严格检查），**坏一份整份拒绝**（`ERR.BAD_TEMPLATE`）。
- 合并：按**名称**判重，同名跳过（本地的不动）；新模板搬入时模板 id 和条目 id 全部换新。

## 三、测试策略

### 3.1 分成三层

| 层 | 怎么做 | 检查什么 | 什么时候做 |
|---|---|---|---|
| 自动测试 | Node 脚本 | 算数据的逻辑：存取、导入检查、排序、统计、日期 | 每次改完对应代码 |
| 手工验收 | 照着清单点一遍 | 页面长什么样、拖拽顺不顺手、手机上好不好用 | 每次发版本前 |
| 性能抽查 | 自己造一堆数据 | 一天 100 条 / 200 条任务会不会卡 | 每次发版本前 |

自动测试只测「算数据的部分」，页面和拖拽只能靠手工点。这正是 1.7 规矩二要「算和画分开写」的原因——分开了，能自动测的部分就多了。

**阶段**（见 2.9）

- **有阶段的任务**行右边有个小三角，点一下展开阶段、再点收起；**默认是收起的**
- 折叠时占的高度和「没有阶段的任务」**一模一样**——不该把四象限撑变形
- 每条任务右上角都有个「＋」，点一下给它加阶段；**没阶段的任务点了会自动展开并弹出输入框**
- 没阶段的任务**没有**小三角，也不会凭空冒出空的阶段行
- 加几个阶段 → 任务行右边出现「3/5」这样的进度，**折叠着也看得见**
- 勾一个阶段 → 进度跟着动，顶部统计也跟着动
- **点父任务的勾选框 = 下面所有阶段一起勾上**；再点一下 = 全取消
- 部分完成（比如 3/5）时点父任务的勾选框 → 是**全部勾上**，不是全清掉
- 阶段只能靠拖拽排序，没有上移/下移的小箭头
- 阶段也能用鼠标拖拽排序；**拖阶段不会连整条任务一起拖走**
- 拖阶段只能在同一个任务内部，拖不出这个任务
- **导入一份「加阶段之前导出的」JSON** → 正常导入，一条不丢
- 导出 Markdown / PDF → 阶段缩进在任务下面，两级列表看得出从属关系
- **把阶段全删光** → 父任务保持删之前的状态，不会突然变回未完成（见 2.9 最后一段）
- 折叠了几个任务之后刷新页面 → 全部收起（有意为之，展开状态不进数据）

**次要功能**

- 导出 JSON：文件能下载，而且能重新导入回来
- 导出 Markdown：内容和当前页面上的数据一致
- 导出 PDF（**仅网页版**）：点了会**弹出打印对话框**，在里面选「另存为 PDF」→ 存出来的文件内容和页面一致
- **点 PDF 之后不该出现「保存网页」那种提示**（那就说明 Ctrl+S 的拦截漏了）
- 打印预览里：**不该有按钮、工具栏、提示条**；象限是边框不是彩色底；黑白打印也分得清
- 一条任务尽量不跨页断开；一个象限也尽量不跨页
- **安卓端不该出现 PDF 这一项**（那边的 `window.print()` 是空壳）——见 4.4
- 电脑上按 Ctrl+S：下载**一个 ZIP**（内含 JSON + Markdown）。**不是一个手势下两个文件**——浏览器会把连续多个下载当成可疑行为拦下来，用户按完 Ctrl+S 看到的是一个拦截提示，体验很差
- 手机上导出：能选格式，包括打包成 zip；**zip 里只有 JSON 和 Markdown**，用手机自带解压能打开
- 导出菜单有三项（JSON / Markdown / ZIP），点哪项就下哪种
- 导入：正常文件合并成功并显示「新增几条、跳过几条」；格式错的文件被拒绝且原数据不变
- 导入是合并：导入一份旧文件之后，**本地独有的任务一条都不能少**
- 导入前有二次确认，并提示「建议先导出备份」
- 导出的 JSON 里**全文搜不到任何账号、密码、口令**，只有 `user` / `schemaVersion` / `dates` 三样
- **随便找一个不是本程序导出的 JSON**（比如某个配置文件）扔进去 → 被拒绝，并说清楚**哪里**不对，而不是一句「格式错误」
- 把导出的 JSON 手工改坏一处（比如某天少了 `III` 那一行）→ 导入被拒绝，**本地数据一条没动**
- 本地某条任务已勾选，导入的文件里同一天同一象限有同名任务且未勾选 → 跳过，**本地那条仍然是勾选状态**（见 D-16）

**本地体积控制（30 天归档）**

- 本地攒到超过 30 天后能触发归档并提示用户
- 归档下载**失败或被浏览器拦截**时，本地数据一条都不能删，并且给出手动归档按钮
- 归档成功之后，本地确实只剩 30 天以内
- 归档出来的文件能当普通 JSON 导入回来，数据完整、没有缺日期
- 导入一份跨度超过 30 天的归档文件后，能正确提示「会再次触发归档」
- 造一份跨度超过 30 天的数据（或把系统日期往后调）→ 打开时出现归档提示条 → 点「归档并下载」→ 文件下载下来、本地只剩 30 天以内
- **点「归档并下载」之前，本地数据一天都不能少**——不能出现「提示条出现了、数据已经没了」这种状态（见 DS 2.4 那条硬规矩）
- 归档下载下来的 JSON，**能当普通文件导入回来**，数据一条不缺

**数据异常与保护模式**

- 把主数据和 4 个备份全部改成非法内容后打开：显示空四象限 + 醒目提示条，**添加 / 编辑 / 勾选 / 拖拽全部不可用**
- 保护模式下随便点几下，磁盘上那份坏数据**一个字节都没变**
- 点「导入备份文件」：能选一份之前导出的 JSON 导进来并解除保护模式
- 点「用空数据重新开始」：有二次确认和明确警告
- 只把主数据改坏（备份是好的）：自动从最近的备份恢复，并提示恢复到了什么时候的版本

**两台设备之间（本版唯一的跨设备通道）**

- 电脑导出 JSON → 手机导入 → 数据一致
- 手机导出 JSON → 电脑导入 → 数据一致
- 两边各加了任务后互相导入 → 按「象限+文本」判重，没有重复条目
- **整个流程不需要联网、不需要账号**——这是本版的验收底线

**安卓端的数据安全**

- 正常关掉 App 再打开：数据还在
- 重启手机再打开：数据还在
- 在设置里「清除缓存」：数据不受影响（这是数据，不是缓存）
- 手动把 localStorage 清空后打开 App：能提示从本地副本恢复，数据救得回来
- 第一次装 App（从没存过数据）：正常显示空状态，**不弹恢复提示**
- 卸载重装：数据确实没了（属于预期），但提示里应引导用户用导出的 JSON 导入
- **导出菜单里没有 PDF 这一项**（安卓打不了印，见 4.4）
- 手机上导出 zip：用手机自带解压能打开，里面是 JSON + Markdown 两个文件

**开两个标签页**

- 标签 A 改了数据，标签 B 刷新后能看到
- 两边同时改，以最后保存的为准

| 象限的界面结构（按钮位置、标题栏组成） | `test-render` 里「添加按钮的位置」那一组（D-30 的防回退用例） |
| `render.js` 的 DOM 部分、或样式 | `test-render` + 手工验收清单全跑一遍 |
| `index.html` 的元素 id | 手工验收清单全跑一遍（`test-render` 测不到 id 拼错） |
| `index.html` 的脚本顺序、或任何 js 的依赖声明 | `test-load-order`。**这一步绝不能省**——顺序错了的表现是整页白屏，控制台里只有一句「require is not defined」，指不到真正的原因 |
| 数据格式（加字段、改结构） | 全部测试 + 做一次「改格式前存下的数据 → 新代码 → 导出 → 导入」的完整往返 |

**最后一条特别重要**：只要动了数据格式，就要拿一份**改格式之前存下来的数据**试一遍，确认老数据升级后不会丢，新加的字段也能正确地存下来、导出去。

好在从这一版起，数据里带了 `schemaVersion`（见 2.3），代码可以**自己判断**手上这份数据是不是老格式，不用再完全靠人记住。但**测试仍然要人来做**——版本号只能让程序知道「这是老格式」，至于「老格式升级得对不对」，还是得真拿一份老数据跑一遍。

## 四、错误处理

### 4.1 错误分四级

| 级别 | 什么情况 | 怎么处理 |
|---|---|---|
| **严重** | 可能把数据弄坏或弄丢 | 停止这次操作，明确提示，引导用户先导出备份 |
| **重要** | 这次操作失败，但数据没事 | 拒绝操作，保住原数据，说明原因 |
| **一般** | 功能没做成，影响不大 | 换个方式凑合，轻提示一下 |
| **不用管** | 用户完全感知不到 | 只在后台记一笔，不打扰用户 |

### 4.2 常见错误怎么处理

| 出什么事 | 级别 | 怎么处理 | 用户看到什么 |
|---|---|---|---|
| 存储空间满了 | 严重 | 这次保存不算数，退回到改动前的状态；**并引导用户做 30 天归档**（不是叫他自己想办法腾地方） | 「存储空间不足，本次修改未保存。点这里归档 30 天以前的历史数据，归档后本地会空出空间。」 |
| 数据读坏了，但备份能救 | 严重 | 自动从最近的可用备份恢复 | 「数据异常，已从备份恢复到 X 月 X 日 X 点的版本。」 |
| 数据坏了，备份也救不回来 | 严重 | **进入保护模式**：空四象限 + 禁止一切写操作，磁盘上原数据一个字节不动，等用户决定（见 2.4） | 「数据无法读取，已进入保护模式。你的原始数据没有被改动。请导入之前导出的备份文件，或用空数据重新开始。」 |
| 30 天归档的下载被浏览器拦了 | 严重 | **不删除本地数据**，改为提供一个手动「归档并下载」按钮 | 「自动归档被浏览器拦截，历史数据仍保留在本地，请点此手动归档。」 |
| 导入的文件不是合法 JSON | 重要 | 拒绝导入，原数据一点不动 | 「文件格式有误，导入已取消。」 |
| 导入的文件结构不对 | 重要 | 拒绝导入，原数据一点不动 | 指出具体是哪个字段不对 |
| 任务内容是空的 | 一般 | 拒绝创建 | 「任务内容不能为空。」 |
| 下载被浏览器拦了 | 一般 | 改成把内容显示出来让用户复制；**绝不因为「以为下载成功」就删本地数据** | 「下载被拦截，请手动复制内容。」 |
| 这台设备不支持打印（仅网页版会遇到） | 一般 | 改成把 Markdown 文本显示出来让用户复制 | 「当前环境无法打印，已提供 Markdown 文本。」 |
| 主题设置读不出来 | 不用管 | 用默认的亮色 | 无 |

### 4.3 所有提示走同一个出口

**所有给用户看的提示，都必须通过 `toast.js` 弹出来。** 不准直接用浏览器自带的弹窗，也不准只在后台打印一行日志就算完。

理由：

- 浏览器自带弹窗在手机上样式很丑，而且会卡住整个页面
- 只在后台打日志等于**没提示**——用户根本看不到，只会觉得「我点了没反应」。以前就吃过这个亏：数据同步一直在悄悄失败，用户完全不知道，等发现时已经丢了很多改动

提示分三种：成功、警告、错误。**错误的提示至少停留 5 秒**，别让用户还没看清就消失了。

### 4.4 PDF 导出的做法（**仅网页版**）

> **先说结论：PDF 导出只在网页版提供，安卓 App 端不提供。**

**为什么安卓端不做**：安卓 WebView **根本没有实现 `window.print()`**——这是 Chromium 主动禁掉的行为，不是我们代码写得不对。Capacitor 打包出来的 App 里调 `window.print()` 不会有任何反应。要在安卓上打印，只能装原生的打印插件（第三方依赖，且主流那个是付费的）。为了一个「顺带导出」的功能引入付费插件，不值得。

所以：**安卓端把 PDF 这个选项从界面上拿掉**，只给 JSON / Markdown / ZIP。不要留一个点了没反应的按钮。

**网页版的思路：先把内容排成 Markdown，再让浏览器把它打印成 PDF。**

```
数据 → 生成 Markdown 文本 ─┬─ 存成 .md 文件
                            └─ 变成网页 → 套上打印专用样式 → 交给浏览器打印成 PDF
```

**为什么绕这一圈**：Markdown 和 PDF 用的是同一份内容。如果两种格式各写一套排版代码，将来改了任务显示格式，很容易只改了一处、忘了另一处，导出的两种文件就对不上了。

**打印专用样式**要单独写一段，规则是：

- 把所有按钮、工具栏藏起来（打印出来不该有按钮）
- 象限的彩色背景去掉，改用边框区分（省墨水、也更清楚）
- 保证黑白打印也能看清
- 一条任务尽量不跨页断开

**要提前告诉用户的两件事**：

1. 最终 PDF 是浏览器或系统生成的，**不同浏览器、不同电脑上排版会有细微差别**（字体、边距、分页位置）。不要承诺「每次导出都一模一样」。
2. 「导出 PDF」在网页上其实是**弹出一个打印对话框**，需要用户在对话框里选「另存为 PDF」并确认，文件才会落到磁盘上。**不是点一下就自动下载**——这是浏览器的机制，改不了，所以要跟用户讲清楚别以为点坏了。

**为什么 PDF 不能打进 zip**（这条决定了 2.7 里 zip 的内容）：

打印对话框走完之后，**PDF 的字节流是交给操作系统/浏览器的，不会回到我们的 JavaScript 里**。也就是说程序手上从头到尾就没有过 PDF 这份数据，自然也没法把它塞进压缩包。想在纯前端拿到 PDF 字节，只能引第三方的 PDF 生成库（pdf-lib、jsPDF 之类）——那是另一套完全不同的实现，本期不做（见 D-18）。

**如果某台设备根本不能打印**（部分 App 内置浏览器），就退一步：把 Markdown 文本显示出来让用户复制。

## 五、风险与决策记录

### 5.1 已经定下来的决定

这些是已经拍板的，改之前要先改这份文档并说明理由。

| 编号 | 决定 | 为什么这么定 |

| D-06 | 所有日期数据存在一个地方 | 导出、导入、备份、恢复都只处理一个文件，简单 |

| D-10 | 任务顺序由列表的先后决定，不额外记「排第几」 | 拖拽时直接重排列表就行，少维护一个字段 |

| D-12 | 算逻辑的代码和画页面的代码分开写 | 分开了才能自动测试；上一版就是因为混在一起，只能手工点，漏了十几处问题 |
| D-13 | 安卓端额外用 Capacitor Preferences 存一份副本 | 安卓系统会在存储紧张时回收 localStorage，只靠它会无声丢掉全部数据 |

| D-16 | 导入判重不看勾选状态 | 同象限同文本就是同一条任务；不覆盖本地已有的状态 |

| D-18 | 打包 zip 固定为 **JSON + Markdown 两件**（不含 PDF） | 不做组合勾选，交互简单、实现也简单。PDF 不进 zip 是硬限制——程序拿不到 PDF 字节，见 4.4 |
| D-19 | 网页版发布到静态网站（GitHub Pages），不做「双击打开本地文件」路线 | **理由已更正**：不是为了同步（跨域由服务端决定，换网址没用），而是本地文件环境下下载和剪贴板受限、数据隔离也更干净，见 1.9 |
| D-20 | 本期不做**历史数据迁移**；但**保留**「登录后认领 `default` 用户数据」这条路径 | 本期是从零开始，没有历史数据可迁。但 FS 明确要求为将来的登录预留迁移路径，靠 2.2 的 key 命名（带 `default`）已经天然具备这个能力 |
| D-21 | 本地只保留最近 30 天，更早的归档成 JSON 下载到用户磁盘 | localStorage 只有约 5MB 还要放 4 份备份，不控制体积迟早写满，写满后修改直接存不进去，见 2.1、2.4 |
| D-22 | 数据全部读不出来时进入**保护模式**：禁止写入，原数据不动，由用户决定下一步 | 「不覆盖原文件」这句承诺，只有靠「禁止写入」才兑现得了——允许编辑一次就会被整份重写覆盖，见 2.4 |
| D-24 | 数据里带 `schemaVersion` 字段 | 现在加是零成本；等有了真实用户再加，就得动所有人的数据，见 2.3 |
| D-26 | 拖拽**网页版和移动端都做**；实现用 Pointer Events，不用 HTML5 拖拽 API | HTML5 拖拽（`dragstart`/`drop`）在 Android WebView 的触摸下**根本不触发**，只用它等于移动端没有拖拽。Pointer Events 一套代码同时覆盖鼠标和触摸，成本并不更高 |
| D-29 | **v1 不做云端同步**，跨设备只走「导出 JSON → 另一台导入」 | 同步依赖外部服务（坚果云没有 CORS、要自建代理 + 备案），是最容易出问题、也最耗时的一块。把它摘出去，v1 就变成一个**完全不依赖网络和第三方**的纯前端应用，能独立交付、独立验收。完整设计已写好，见第六章 |
| D-30 | 添加任务的入口放在**每个象限标题栏的右上角**，只显示一个「＋」，不是象限底部的大按钮 | 底部整行按钮有两个实际问题：任务一多就得先把列表滚到底才点得到；而且它占掉一整行高度，任务少的时候显得空。右上角**始终可见、不占任务区**。代价是按钮只剩一个符号，所以必须补 `aria-label` 和 `title`；**并且点击区域要固定 32×32，不能跟着视觉一起缩小**——移动端点不准是最让人恼火的问题（见 3.3） |
| D-31 | 增删改**全在原地完成**：点「＋」在列表末尾长出一个输入框，点任务文字把那条变成输入框；回车或点到别处提交，Esc 取消。**不弹任何对话框** | 弹窗会打断操作，浏览器自带输入框在手机上样式也很丑。两条边界行为是刻意定成这样的：**改文字时清空 = 拒绝并恢复原文**（用户可能只是想清空重打，手一滑就丢一条任务）；**新增时留空 = 安静取消**（他本来就只是点了下加号又反悔，这时候弹「内容不能为空」是在骂人） |
| D-32 | 任务可以拆一层**阶段**。父任务的完成状态**只由阶段决定**；没阶段的任务，它自己就是一个条目。统计按「最细的可勾选单位」算 | 一件事超过两三步，用户就得二选一：拆成一堆独立任务（列表被瞬间淹没），或者只写一条大任务（做完了多少完全看不出来）。阶段就是给这个中间地带准备的。四条规矩、界面上的一键全选、以及那个「删光阶段后状态停住」的行为，都写在 2.9 |
| D-33 | 阶段**默认折叠**，点三角才展开；展开状态只存内存、不进用户数据 | 四象限本身就是 2×2 网格，地方很紧——每个任务都铺开阶段，一屏就装不下几条任务了。折叠时占的地方和没有阶段时完全一样。展开状态属于「界面怎么看」，不属于「用户的任务」，所以不进导出和备份 |
| D-34 | 阶段排序**只靠拖拽** | 上下箭头占地方、在手机上还不好点；拖拽一套 Pointer Events 已经同时覆盖鼠标和触摸，没必要再叠一套按钮 |
| D-35 | 任务块 = 象限列表里带 `type: 'block'` 标记的容器条目，块内 `tasks` 只装普通任务；**块只有一层、块自身不计入统计**（数块内最细可勾选单位）；块级判重按「象限 + 文本」，块内条目随块整体搬不单独判重 | 容器做成列表里的一种条目（而不是象限之外的独立结构），块与任务的混排拖动、跨象限拖动就全是「重排同一个列表」一件事，不用为块另写一套移动逻辑。块内复用任务形状，勾选 / 编辑 / 阶段 / 统计零新增代码。不嵌套和 2.9 阶段只有一层是同一条设计底线 |
| D-36 | 块**默认展开**（与阶段相反），展开状态存内存不进数据，且用独立的状态表（`collapsedBlocks`，语义「默认开、记关」） | 阶段是任务自己的细节，折叠省地方；块是容器，折叠了没法看见里面有什么、也没法往里拖。空块折叠更是直接隐身 |
| D-37 | 计划池是**与 `dates` 平级的全局列表**，不按日期分；池内元素**就是任务形状**（进池出池零转换）；进池只走明确点击（一期的「推迟」按钮；三期再加池内「＋」手动添加），**拖拽只做「池 → 象限」** | 「推迟」的语义是「现在不排、以后再安排」——它本来就没有日期归属：按日期分池，推迟时就得问「归哪天」，可用户恰恰是因为不知道归哪天才推迟的；而且切日期时池内容变来变去，用户会以为丢了。元素沿用任务形状，恢复、编辑、导入导出全部复用现有代码。不接受往池里拖，是因为「拖到象限下方空白」的失手和「明确要推迟」分不开——推迟是明确意图，值得一次明确的点击；三期加的手动添加同样是明确点击（池头部「＋」），与这条不冲突。R3 要加的 `plannedDate` 是**任务身上的字段**，不是池的分组键，池永远只有一份（见 2.11） |
| D-38 | 池内完成时间 = 任务身上的**可选字段 `plannedDate`**（'YYYY-MM-DD'，缺字段即「未设定」）；从象限推迟时默认**所属日期 + 1 天**；推迟阶段保存为池内任务，前缀 `[父文本]` 直接拼进文本，不挂父任务引用 | 时间是任务自己的属性，不是池的结构——这样 normalize / 导入导出对它只做「有则校验、无则缺省」，老备份零影响。默认值用所属日期 + 1 而不是真实今天 + 1：查看过去的日期推迟时，不会得到一个已经过去的时间（见 2.11「为什么推迟的默认是所属日期 + 1」）。阶段前缀拼文本不挂引用，是因为父任务可能被删、被改、自己也进了池——挂引用全是悬空问题，拼文本永远自解释，requirements 的原话也只要求「文本内容前用中括号标注」 |
| D-39 | 时段选择用**原生 `<select>` 下拉**（「未设定」+ 六时段共七项，emoji 图标作为选项文本前缀），不做自绘弹层或图标网格，值直接存中文 | 七态靠图标轮换要点六下才绕得回来，pass；自绘弹层要新做一套定位 / 开合 / 点外关闭的基础设施（导出菜单是全局唯一一处，没必要为每一行复制一份）；原生 select 交互零代码，移动端唤起的是系统原生滚轮，触摸体验反而最好，且天然进 `isInteractive` 排除拖拽。值存中文是因为导出 JSON 给人看（2.6），六个中文值本身就是白名单，不需要代号映射；emoji 只活在渲染层，数据永远干净 |
| D-40 | 时间视图是**纯展示的重组视图**：只读、只显示有任务的时段、块拍平、计划池不进；视图切换是界面状态存内存，刷新回四象限 | requirements 第 5 条只说「展示对应内容」，没要求在里面操作——加勾选 / 编辑等于把象限那套交互复制一遍，收益小而回归面大；要改安排回四象限改，数据源只有一份，永远不会出现「两边改的不一样」。只显示有任务的时段是 requirements 的原话（「根据时间段数量展示」）。视图切换和阶段展开同性质——「界面怎么看」不属于「用户的任务」，不进数据、不跟导出（D-33 同类） |
| D-41 | 模板的「覆盖同名」**纯按名字判定**，不存「是否重命名过」标记位；应用模板时**勾选清零、编号全换、同文本跳过** | requirements 说「没有重命名的话，重新缓存会覆盖同名的缓存项」——「没重命名」和「名字还是自动名」是等价的两种说法，按名字撞不撞判断即可，多存一个标记位只会引入两套状态对不上的风险（改了名又改回日期串怎么办？按名字算，这种行为反而自然：又撞名了，又覆盖）。应用时清零勾选是因为模板是**计划**不是记录——把周一的「已完成」搬到周二，周二一打开就是半完成状态，统计全乱；编号全换和导入同一条 D-09 的理由；同文本跳过让「应用两次」不会出双份 |

### 5.3 还没定下来的问题

#### 触摸拖拽和页面滚动会打架 —— 等真机验证

移动端上，「手指按住任务上下拖」有两个都说得通的解释：**重排任务**，和**滚动页面**。浏览器默认偏向后者——一旦它认定手势是在滚动，就会把事件收走，我们的拖拽当场就断了。

现在的做法是给任务加 `touch-action: none`，把滚动让给拖拽。**代价是：手指按在任务上就滚不动页面了**，只能按在任务之间的空隙上滚。任务密集的时候会比较难受。

这个取舍要真机试过才能定，可能的走向：

| 方案 | 说明 |
|---|---|
| 保持现状 | 拖拽优先。任务密集时不好滚 |
| **长按才进入拖拽** | 手感最接近原生 App，是业界常见做法。代价是代码更复杂——要处理「浏览器已经接管了手势、直接发 pointercancel」的情况 |
| 加一个拖拽把手 | 只有按住把手才拖，任务本身照常滚动。最稳，但每条任务要多占一点地方 |
| 加一个「排序模式」开关 | 平时正常滚动，开了开关才能拖。移动端老牌做法，但要加界面元素 |

**真机上试过之前先不改。** 这是本版唯一一处「知道有取舍、但还定不下来」的地方——记在这里，免得以后当成 bug 去「修」。

以后出现别的新问题时也追加在这里，并同步更新 FS 和本文。

## 六、后续版本：云端同步（**v1 不做**）

> **本章内容本版全部不实现。** 放在这里是为了两件事：一是把已经想清楚的东西存下来，不白费；二是**防止下一版重新讨论一遍**——尤其是那几个已经踩过的坑。
>
> 读到这里，前面的正文就到头了。本章可以当作独立的设计稿来看。

### 6.1 为什么把它整个摘出去

v1 的目标是「跑通最小可用闭环」，而同步是整条链路上**唯一依赖外部服务**的环节：

- 坚果云没有跨域头，网页端连不上（已实测，见 6.3）
- 要连上就得自建代理 → 买服务器 → **备案 1~3 周** → 长期维护
- 代理、网络、冲突合并，每一块都有自己的失败模式，且大多在别人手里

摘掉之后，v1 变成一个**不联网、不依赖任何第三方服务**的纯前端应用。它能独立开发、独立验收，不会被任何外部因素卡住——**这就是把同步移出来的全部理由**。

**代价说明白**：用户得手动导出、手动导入 JSON。这条必须在界面上讲清楚，别让用户以为两台设备会自动一致（见 R-20）。

### 6.2 原定的同步设计

**做什么**：所有设备读写坚果云上的**同一个 JSON 文件**；改完数据就传上去，打开时先拉下来，**拉下来的数据和本地的做合并**（不是覆盖，见 6.2.2）。

因为网页端连不上坚果云（见 6.3），同步要分两条路：

```
网页版    ──→  自建中转代理（补上 CORS 头）──→  坚果云 WebDAV
安卓 App  ──────────────────────────────────→  坚果云 WebDAV（直连，不经代理）
```

| 端 | 怎么连坚果云 | 为什么 |
|---|---|---|
| 安卓 App | **直连** | App 的请求走原生网络栈，不受浏览器安全规则约束，根本没有跨域这回事 |
| 网页版 | **经自建中转代理** | 浏览器的跨域限制绕不过去，只能在中间放一台自己的服务器转发 |

**为什么选坚果云**：

- 数据留在**用户自己的网盘**里。我们的服务器只是通道，出问题也不会丢数据，更不用替用户保管数据
- 国内访问快：实测约 **0.12 秒**，比 GitHub API 快 3~5 倍（见 6.3 的网络数据）
- 坚果云免费额度是每月 1G 上传 / 3G 下载、每 30 分钟 600 次请求，而我们传的就是几十 KB 的 JSON，完全够用

**连接信息**：

| 项 | 值 |
|---|---|
| 坚果云地址 | `https://dav.jianguoyun.com/dav/` |
| 用户名 | 用户自己的坚果云账号 |
| 密码 | 用户在坚果云后台生成的「**应用密码**」（**不是登录密码**） |
| 中转代理地址 | 自建服务器的域名（见 6.2.1） |
| 同步文件路径 | 固定一个路径，如 `/dav/TimeScheduler/quadrant.json` |

> **不要把任何账号密码写进这份文档，也不要把中转代理的地址和口令写进来。** 让用户在程序里首次配置时自己输入，只存在他自己的设备上。如果是多人共用一份代码，发布前要全文检查一遍有没有漏。

#### 6.2.1 中转代理（自建）

**定位**：一台**无状态**的转发器。收到网页的请求 → 原样转发给坚果云 → 把响应原样返回，**顺手补上 CORS 头**。

| 做 | 不做 |
|---|---|
| 转发请求到坚果云并返回结果 | ❌ 不存用户数据 |
| 补 CORS 响应头、应答预检（OPTIONS） | ❌ 不存、不看、不记用户的账号密码 |
| 校验调用方身份（访问口令） | ❌ 不做合并、不进任何业务逻辑 |
| 限制上游只能是坚果云的固定路径 | ❌ 不能当通用代理用 |

**必须守住的六条，一条都不能省**：

| 规矩 | 不守会怎样 |
|---|---|
| **上游地址写死**，只允许转发到 `dav.jianguoyun.com` 的固定路径前缀 | 变成开放代理。别人拿它当跳板访问任意地址，流量和法律责任都算你的 |
| **必须 HTTPS** | 请求头里带的是 Basic 认证（账号密码只是 Base64，等于明文）。走 HTTP 等于在公网上裸奔 |
| **日志里绝不打印 `Authorization` 头** | 等于把所有用户的网盘密码写进日志文件，是个随时会爆的雷 |
| **必须有一个访问口令** | 公网 IP 会被扫。没口令的话，别人可以用**他自己的**坚果云凭据白嫖你的服务器带宽 |
| **CORS 头只放行自己的站点**，不要用 `*` | 用 `*` 等于允许任何网站借你的代理去连坚果云 |
| **加最低限度的限流** | 防止被刷爆带宽 |

**为什么口令是硬要求、而 `Origin` 校验不能替代它**：`Origin` 头只能拦住浏览器，随便一个脚本都能伪造它；而代理是直接暴露在公网的。所以口令必须有，`Origin` 校验只是额外一层。

**访问口令存哪**：单独一个 key，**不进导出、不进同步、不进备份**（D-23）。

**部署链路**（周期卡在备案上）：

```
买服务器 → 买域名 → 提交备案 → 等审核（1~3 周）→ 解析域名 → 装证书 → 部署代理
                       ↑
                这一段全是干等，所以要最先启动
```

> **一个必须让用户想清楚的取舍**：走代理意味着用户的坚果云**应用密码会经过这台服务器**。自用场景下这等价于「自己信任自己的服务器」，没有额外风险；但**一旦开放给多个人用，性质就变了**——那时必须让使用者明确知道「你的密码会经过这台服务器」。

#### 6.2.2 同步时机与合并规则

| 什么时候 | 做什么 |
|---|---|
| 用户改完数据 | 攒 **3 秒**再传（网页版和安卓端**都是 3 秒**） |
| 打开程序 | 拉一次云端数据，**和本地合并** |
| 手动点击 | 用户自己点「上传」或「下载」 |

**唯一一个例外：什么时候不许自动上传。** 只要数据处于「可疑」状态就暂停一切自动上传：

- 程序刚才是从备份 / 本地副本恢复过来的
- 程序处于保护模式（见 2.4）
- 上一次读数据报了错

**为什么**：自动上传是一把双刃剑。异常时候它**会拿一份坏数据把云端的好数据盖掉**——用户的 localStorage 被系统清了、程序没读到本地数据，如果还照常自动上传，几秒之内云端的完整数据就被一份空数据覆盖了。**本来只是本地出问题，结果连云端这份唯一的完好副本也一起毁了**（D-25）。

**打开程序时做什么**：

```
拉取云端 JSON
   ↓
和本地数据逐日期、逐象限合并
   ↓
合并规则：按「象限 + 文本」判重，**只看同一天**（和 2.5 导入用同一套规则）
   ├─ 两边都有 → 保留本地那条（连同本地的勾选状态）
   ├─ 只有云端有 → 插到本地
   └─ 只有本地有 → 留着不动
```

**为什么拉取时做合并，而不是直接用云端覆盖本地**：因为「用云端覆盖本地」会在一个很常见的场景下直接丢数据——**用户断网时改了几条没传上去，下次一打开，本地较新的改动就被云端旧数据无条件盖掉了**，全程没有任何提示（D-02）。改成合并之后这个场景就安全了。

**顺带解决了「两台设备同时改」的大部分问题**：A 和 B 各改各的，A 先传、B 后传（B 覆盖了云端的 A 版本）。A 下次打开 → 拉取云端 → 和本地合并 → **A 之前被覆盖的改动又回来了**；A 再传，云端就变成两边都全的版本。

**必须说清楚的已知限制**：合并是「只增不减」的——本地删除过的任务，如果云端还在，合并之后**会被重新拉回来**。所以**删除操作在两台设备之间不保证同步**（R-15）。界面上要讲明白，别让用户以为删掉的任务会处处消失。

### 6.3 实测结论：坚果云网页端连不上（2026-10-01）

**结论：坚果云的网页端同步做不了，必须走代理。**

| 请求 | 结果 |
|---|---|
| 坚果云 `OPTIONS` 预检 | `401`，**无 `Access-Control-Allow-Origin`** |
| 坚果云 `GET` / `PROPFIND`（带 `Origin`） | `401`，无任何 CORS 头 |
| 对照组：GitHub API | `204` + `Access-Control-Allow-Origin: *` ✅ |

**为什么这是死结**：请求必须带 `Authorization` 头（Basic 认证），而它不在浏览器的「简单请求」白名单里，所以浏览器**会先发一个匿名预检请求**去问服务端允不允许。按规范，**预检请求本身不带凭据**——坚果云收到的就是一个匿名 `OPTIONS`，它的 nginx 直接当未认证访问处理，回 401，没有任何 CORS 头。浏览器看到「对方没放行」就拦截，**真正的请求压根发不出去**。

所以「认证成功后会不会放行」这个问题不重要：**预检这一关就过不去，我们走不到发正式请求那一步。**

**换网址（GitHub Pages）也救不了**：跨域判定的是「页面的来源」和「目标服务的允许名单」之间的关系。坚果云的允许名单是空的，**无论页面挂在哪，它都不允许**。

**顺带量到的网络数据**（同一台机器）：

| 目标 | TLS 握手 | 总耗时 |
|---|---|---|
| 坚果云 | 0.09s | **~0.12s** |
| GitHub API | 0.32s | ~0.43s |

**考虑过但没选的方案**（存档，免得下次重复讨论）：

| 方案 | 为什么没选 |
|---|---|
| 同步只在 App 端，网页版手动导入导出 | 不满足「两端都要能自动同步」的要求 |
| 换成 GitHub Gist | API 确实支持 CORS（两边都能用），但国内访问慢 3~5 倍，且每次上传会累积一个修订版本 |
| 反向代理到别家 | 其他 WebDAV / 网盘服务要么没有 CORS，要么要 OAuth，比自建代理更麻烦 |

### 6.4 与本章相关的决策与风险

**决策**

| 编号 | 决定 | 为什么 |
|---|---|---|
| D-01 | 同步数据存坚果云 WebDAV | 数据留在用户自己的网盘，我们不用替用户保管；国内快；免费额度够。**注意：为了让网页端连得上，仍然要自建中转代理**（D-27） |
| D-02 | 上传时整份覆盖云端；**拉取时和本地做合并** | 纯「最后保存的赢」会在「断网改完就关页面」这种常见场景下静默丢数据，见 6.2.2 |
| D-15 | 网页端同步必须先实测再动手 | ✅ 已完成：实测确认不可行（6.3）。几分钟的验证直接决定了必须先有代理，顺序反过来就要白写一遍网页端同步代码 |
| D-23 | 同步凭据单独一个 key，**不进导出、不进同步、不进备份** | 否则用户把备份文件发给别人或传到公共电脑，等于把网盘账号一起送出去 |
| D-25 | 数据来源可疑时（刚从备份恢复、保护模式中、上次读取出错）**暂停一切自动上传** | 自动上传在异常时会拿坏数据覆盖云端唯一一份完好的副本，见 6.2.2 |
| D-27 | 自建一台**无状态 CORS 中转代理**，专供网页端访问坚果云 | 浏览器跨域绕不过去（6.3 已实测），自建代理是「不砍功能、不搬数据」前提下的唯一解 |
| D-28 | 代理必须先启动**备案**流程，且与页面开发并行 | 国内节点挂域名必须 ICP 备案，1~3 周，且大部分时间是干等 |

**风险**

| 编号 | 风险 | 会有什么后果 | 怎么防 |
|---|---|---|---|
| R-01 | 网页端连不上坚果云（**已确认发生**） | 网页端无法直连坚果云，原同步设计在网页端完全走不通 | ✅ 已定方案：走自建中转代理（D-27）。第 0 步的实测把这个风险从「也许」变成了「确定」 |
| R-02 | **账号密码被写进文档或代码里** | 账号被盗用 | 密码只让用户在程序里填；单独 key 存放，且不进导出 / 同步 / 备份（D-23）。发布前全文搜一遍 |
| R-03 | 两台设备同时改 | 上传晚的覆盖云端的版本 | 拉取时合并能挽回大部分（6.2.2）；界面上说明「两边都打开一遍才能都同步上」 |
| R-09 | 用户以为两台设备会自动一致 | 两边各改各的，产生困惑 | 界面上明确写清同步时机，并说明删除不保证同步 |
| R-15 | **拉取合并会复活已删除的任务** | A 设备删掉的任务，从 B 设备同步回来后又被拉回本地 | 合并只增不减的固有代价。真要解决需要删除墓碑记录，本版不做 |
| R-16 | **备案周期长**（1~3 周） | 卡住同步功能的开始时间，成为整条链路的瓶颈 | 最先启动、并行等待（D-28）。不想备案就得用海外节点，但那样会失去「国内快」这个选坚果云的理由 |
| R-17 | **代理被当成开放代理滥用** | 别人拿你的服务器访问任意地址，带宽和法律责任都算你的 | 六条防护一条都不能省（6.2.1） |
| R-18 | **用户的网盘密码会经过代理** | 代理被入侵或被窥探时密码泄露 | 代理无状态、不存不记密码、日志绝不打印 `Authorization`、强制 HTTPS。自用无额外风险；开放给他人用时必须明确告知 |
| R-19 | **代理单点故障** | 代理一挂，网页版的同步整体不可用 | 明确这是**降级**不是故障：App 端仍直连坚果云，网页版本地数据完好、只是同步停摆。提示要写清「同步暂时不可用，数据已保存在本地」 |
